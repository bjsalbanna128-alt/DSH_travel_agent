# 履约模块前置修改 · 可售库存与供应商资源

任务开始日期 2026-11-26 ｜ 功能迭代 ｜ C 端交易的资源前置，待实现

## 1. 交付顺序和边界

免费 AI 规划、生成草稿和确认行程均不占库存、不收费。游客主动选购增值商品后才进入交易。第一阶段先让运营维护真实供应商、商品、按服务日的售价与库存，供游客下单时校验。这里的真实库存指运营依据供应商实际配额录入的可售数量，首版由人工维护，尚无供应商实时库存接口。

第二阶段按同目录的《订单管理》跑通酒店与门票的模拟支付和最小 B 端复核。首期游客可售范围为 `hotel_room` 与 `attraction_ticket`；用车仍只在资源后台维护，不开放游客购买。第三阶段再扩充《订单管理》中的完整订单后台，并按《履约模块设计》落地人车台账与调度。其中本规格负责供给与库存；订单规格负责订单状态、支付退款和复核；履约规格负责确认后的执行。车队台账可以后交付，不作为酒店/门票订单试点的依赖。

## 2. 库存与报价的唯一口径

| 对象 | 规则 |
| --- | --- |
| 销售单位 | 酒店按房型、入住日、间夜；门票按票种、游览日、张；车辆按车型、用途、服务日、趟。人民币金额以分存储。 |
| 报价主键 | 延用 `price_offers(product_id, service_date)`。增加总投放、预占、确认占用三个数量。计数为非负整数，总投放已设置时须满足“预占＋确认占用 ≤ 总投放”。 |
| 可售 | 供应商启用、商品上架、报价可售、库存数已核实，剩余＝总投放－预占－确认占用。零是有效配置，表示无余量；旧报价未设库存只供查看，游客不能下单。 |
| 占用明细 | 按订单项目和服务日存数量与状态（预占、确认占用、已释放），唯一键防重复。计数、占用明细和订单在同一写事务更新；金额、数量、服务日取服务端校验结果。 |
| 编辑与删除 | 运营调价只影响新订单。新总投放不可低于现有预占和确认占用之和；停售阻止新单。被订单占用或已有交易引用的报价不得硬删除，允许停售并保留快照。 |

**一间住两晚**须分别检查两个入住日各一间，不含退房日；两间住一晚才在同一天占两间。多项目先合并相同商品与服务日的数量，按固定顺序锁定、条件更新。所有日期均成功才建单，任一失败整体回滚。报价页可售数仅供选购，服务端在提交时重验商品、供应商及报价状态。并发修改供应状态与建单须在一致的事务顺序下处理。

## 3. 下单、复核、取消怎样影响库存

| 业务动作 | 库存动作 |
| --- | --- |
| 游客提交订单 | 按建单成功时的服务器时钟逐晚预占 15 分钟；未付款在到期点失去支付资格并释放，模拟付款成功后保留本单占用直至复核或取消。 |
| 运营复核通过 | 核对本单每项预占仍有效，并记录供应商实际能否提供约定资源。通过时将本单数量从预占转为确认占用，相加总数不变。即使剩余为零，只要最后一份正由本单占用，仍可通过。 |
| 未付款取消、预占到期 | 仅释放尚在预占状态的明细，重试不重复加回。清理与模拟支付串行核对同一订单，已成功模拟付款的订单在原到期点继续保留库存。 |
| 已付款取消、复核拒绝 | 按订单规格登记取消与退款义务。若供应商明确缺货，先停售受影响报价再解除本单预占，禁止把现实中不存在的库存立即卖给下一位游客。无缺货且供应商尚未占用资源时可释放。已确认且尚未入住时，游客申请取消后先保留占用，运营核实酒店同意退订后才恢复可售；已实际入住时转人工售后。运营须记录操作人、数量与原因。退款成功本身不触发回补。 |
| 服务已执行 | 保留实际消耗及历史；运营在履约侧登记执行情况不能修改原单数量。 |

运营能在报价详情查看总投放、预占、确认占用、可售及停售原因，在复核时查看本单占用。复核期间报价停售或商品下架需要核实对存量订单的影响；仅停售新单不等于供应商拒绝供给，库存明确不足时不可强行通过。

## 4. 供应商、车辆与迁移

第一阶段复用现有供应商、商品及报价页面，补齐数量与状态；供应商分类可先录入。以下车队详情与人车维护随用车业务接入。用车商品沿用车型名称与座位容量，增加用途 `airport_transfer / airport_return / city_use / charter` 及可选行李容量。一趟对应一个服务时段，具体上下车点与乘客数随订单快照保存。

### 4.1 供应商分类

`suppliers` 增加 `kind`：String(24)，非空，默认 `other`。

| 取值 | 含义 |
|---|---|
| `hotel` | 酒店 |
| `ticket` | 景区/票务 |
| `vehicle_fleet` | 车队（提供车辆与司机） |
| `other` | 其他 |

约束：`kind = vehicle_fleet` 的供应商可以维护车辆与司机；其他类型不显示该区块。商品与供应商类型的匹配建议提示但不强制（同一酒店供应商也可代售门票，留出弹性）。

### 4.4 删除保护

- 有车辆或司机的供应商删除 → 409，提示先处理台账。
- 有历史指派引用的车或司机删除 → 409，改为停用，保留调度历史。
- 允许把车辆/司机置为 `inactive`，历史任务保留引用。

**存量升级。** 先迁移数据库，再执行现有报价结构检查。旧报价新增数量字段，未知总量保留为空，既有单价和历史展示可读；运营补录供应量后才开放销售。旧车辆商品保留 `vehicle_name` 和 `passenger_capacity`；若新接口使用 `seats`，显式映射旧值。用途待核实，原“元/车天”报价暂停交易，运营确认用途及每趟售价后才能启用。供应商默认 other，有台账的车队不能直接改成其他类型。迁移可重复执行，不覆盖已核定的库存和价格。若存在测试或历史订单，按实际交易流水对账，不能仅凭旧状态 confirmed 推定已支付。

## 5. 开发落点、风险与验收

- 扩展现有资源模型、迁移、后台报价读写及 Vue 表单。数量写权限限运营；游客只能获得可购日期、售价及可售提示，不能读取成本、司机电话或其他订单占用。车队阶段再提供按供应商管理车辆及司机的列表、新增、修改、停用与删除入口。
- 在 `backend/tests/` 覆盖旧库升级两次、原车价不能按趟直接卖、未设与零库存、改库存下限、已引用报价禁止删除、酒店逐晚计价。并发抢最后一份只成功一单，跨日缺货整单无残留。
- 跨模块验收：最后一间房被本单占用后复核能通过；重复取消只释放一次；供应商核实缺货并拒单后，其报价不会瞬间恢复可售。
- 主要影响是存量商品上线后可能暂不可购买。上线前由运营选定试点商品、逐日核实配额与售价，确认至少一条可购买链路。前端从 `frontend/` 执行 `npm run build`，走查报价维护与游客查询。

- 10 个库存场景全部通过（等价脚本，每场景独立临时库）：未核定库存不可售、核定后可售、预占后售罄、确认转占用且幂等、释放只动预占、过期预占自动回收、超卖被拒、同商品同日合并、投放数量不能低于占用、旧库升级两次不报错且旧报价保留为空总量。
