# C 端售卖与加购：可订标记、加购清单与收银入口

任务开始日期 2026-11-26。

> **与既有规格的关系。** 交易本身（订单模型、状态机、模拟收银、复核、取消退款）以 `features/2026-11-26-订单管理/spec.md` 为准，履约以 `features/2026-11-26-履约模块设计/spec.md` 为准。本规格只负责「用户在 C 端**看到什么、勾选什么、怎么进入收银**」，不重复定义订单与资金规则。

## 一、原因与目标

规划是免费的基础服务，酒店与门票是付费的增值服务。行程出来后，用户需要：

1. 一眼看出哪些是**我们能订的**（有供应商、有报价、有库存），哪些只能自己去；
2. 一次性勾选要订的东西，进入收银；
3. 也可以**一个都不订**，只拿路书。

本规格交付这块「选购界面」：可订标记、加购清单、数量与合计、提交到订单接口、支付后的状态说明。

## 二、范围和边界

### 本次交付

1. 行程页的可订标记与汇总条。
2. 加购清单页：分组（住宿 / 门票）、勾选、数量、合计、联系人与出行人。
3. 提交订单（调用订单规格定义的游客下单接口）。
4. 收银入口与「已付款待运营确认」的状态说明。
5. 我的订单入口与订单详情页（C 端只读）。
6. 模拟支付产生**模拟积分**（演示用，带明显标识，可清理）。

### 不在本次范围

- 订单创建、模拟收银、库存预占、复核、取消退款的实现（在订单规格里）。
- 履约任务与进度（在履约规格里）。
- **用车**的游客购买入口：行程里的城内交通是代码估算、没有对应商品，第二期接入（界面预留用车分组）。
- 真实支付通道、发票、优惠券。
- C 端改单（订单提交后内容冻结，改需取消后重下）。
- 正式积分账务（模拟积分仅用于演示，与正式积分数据分开标识）。

### 依赖

| 依赖 | 用途 |
|---|---|
| `2026-11-26-内容层与检索合流` | 行程里的酒店/景点带 `offer`（product_id、价格、剩余、可售） |
| `2026-11-26-履约模块前置修改` | 逐日库存与可售判定 |
| `2026-11-26-订单管理` | 游客下单、模拟收银、复核、取消退款、状态机 |

### 可能受影响的现有行为

- 行程详情页新增标记与按钮；行程本身展示不变。
- 个人中心新增「我的订单」。
- 首次出现游客侧订单数据。

## 三、展示规则

行程页与加购页对同一酒店/景点使用同一套判定，避免两处不一致。

| 状态 | 判定 | 文案 |
|---|---|---|
| **可预订** | 该服务日的现行绑定、报价和库存均可售，剩余大于 0 | 显示住宿区间或门票数量、售价与余量 |
| **已售罄** | `offer` 存在但剩余 = 0 | `已售罄` |
| **参考价** | `offer = null` 且参考价 > 0 | `参考价 ¥{hint} · 本平台暂不提供预订` |
| **待选日** | 尚未确定服务日 | `请选择出发日以查询价格和库存`，如有起价只显示为参考 |

规则：

1. 价格只用 `offer.price_cny`（来自价库当日报价），绝不用内容层参考价充当售价。
2. 参考价必须带「参考」与「本平台暂不提供预订」，避免误导。
3. 出行日期不明时，可在加购页选择出发日。选日后按行程序号确定各服务日，仅更新购买报价，不改写路书。
4. **第一期开放酒店房型与景点门票**；用车商品在行程里没有对应条目（城内交通是代码估算），第二期接入前不展示。
5. 行程页底部汇总：「本次可预订 N 项，合计约 ¥X」，口径与加购页一致。

## 四、交互流程

```
行程详情 /trip/:id
  ├─ 酒店卡片：可预订 / 已售罄 / 参考价
  ├─ 底部汇总 + [ 选择房型与日期 ]
  └─ 无可订项时：显示「本次行程暂无可在线预订的项目」
        ↓
  加购清单 /checkout/:tripId
  ├─ 分组：住宿 / 门票
  ├─ 每项：勾选 + 酒店与房型 + 入住/退房日 + 间数 + 每晚单价 + 小计
  ├─ 出行人信息（默认取常用出行人）
  ├─ 联系人（默认本人）
  └─ 合计 + [ 提交订单 ]
        ↓
  订单确认/收银 /orders?order=:orderId
  ├─ 订单号、所选项目、服务日、应付总额与支付倒计时
  ├─ 「模拟支付，不会扣款」
  └─ [ 确认模拟付款 ]
        ↓
  订单详情 /orders?order=:orderId
  ├─ 已付款，待运营确认（明确告知还在等确认）
  └─ 状态随复核、取消、退款刷新
```

**两道确认**：行程页确认行程；加购页确认购买。两者都可以「什么都不做」直接退出。

## 五、加购清单生成

### 5.1 数据来源

`GET /api/v1/checkout/options?trip_id={id}`（C 端，`require_tourist`）：

1. 校验行程归属（`trips.user_id == 当前账号`），否则 404。
2. 遍历 `trips.itinerary` 的 `day_plans`：
   - 通过已绑定并发布的 `content_id` 查询景点票种和酒店房型。
   - 旧路书可用 `offer.product_id` 反查唯一匹配的内容，歧义时仅作参考。
3. 对每个候选按 `service_date` **实时重算**报价与剩余（行程里的 `offer` 是生成时快照，可能已过期或售罄）。
4. 同房型的连续夜晚合并为一个条目，保留入住、退房日期及每晚报价；不连续的区间可独立选择。
5. 返回分组清单（住宿 / 门票）、建议数量、单价与合计。

**为什么重算**：行程可能是几天前生成的，期间价格和库存都变了。加购页必须展示此刻真实可买的状态，否则用户到收银才被拒。

### 5.2 数量与金额

| 项 | 建议数量 | 上限 |
|---|---|---|
| 酒店 | 晚数（入住到退房） | 30 晚 |
| 门票 | 出行人数（成人 + 儿童 + 老人） | 20 张 |

- 间数默认 1，可改（1–5 间）。
- 单价取 `price_offers.sale_fen`，服务端查询，不信任前端。
- 小计 = 单价 × 数量，合计 = Σ 小计。
- 前端展示金额仅作参考，最终以订单接口返回为准；不一致时提示「价格已更新」并刷新清单。

## 六、提交订单与收银

### 6.1 提交

调用订单规格定义的游客下单接口，不新增并行接口：

```
POST /api/v1/orders
  Idempotency-Key: <uuid>
  body: {
    trip_id, departure_date?,
    contact_name, contact_phone,
    travelers: [{ name, document_type?, document_number?, phone?, is_lead? }],
    selected: [
      { product_id, kind: "hotel", check_in, check_out, quantity, quotes },   // 住宿：逐晚报价版本
      { product_id, kind: "ticket", service_date, quantity, quotes }         // 门票：当日报价版本
    ]
  }
```

服务端职责（订单规格已定义，本规格只列前端必须配合的部分）：

1. 服务端按商品与服务日重新校验价格、库存与可售性，**拒绝前端传入的金额**。
2. 任一项不可售 → 409，返回逐项原因（`sold_out` / `off_shelf` / `no_offer` / `price_changed`）；前端标红对应项并刷新清单。
3. 同一提交键、同一载荷返回原订单。相同键对应不同载荷时返回 409。
4. 下单成功即进入 15 分钟支付窗口，收银页显示倒计时。

### 6.2 收银

按订单规格的本地模拟收银：

```
POST /api/v1/orders/{id}/payments
  body: { idempotency_key }
```

- 页面显著标注「模拟支付，不会扣款」。
- 支付成功 → 订单进入 `paid_pending_review`，页面明确告知「已付款，等待平台确认库存」。
- **不生成履约任务**：任务在运营复核通过后才生成（履约规格第 1 节）。
- **产生模拟积分**：按 `金额 // 10` 入账，用于演示会员积分闭环。入账时给交易打 `mock` 标识（`event_id` 以 `mock-` 开头，并在 `point_transactions` 上记录来源订单），会员中心把模拟积分与真实积分分开显示；提供清理脚本按 `mock` 标识删除。**注意**：这与订单规格中「不得向正式积分服务投递模拟事件」的旧约定冲突，实现时以本节为准，并同步修订订单规格第 3 节。

### 6.3 状态与文案

| 订单状态 | 游客看到 |
|---|---|
| `pending_payment` | 待支付 + 倒计时 |
| `paid_pending_review` | 已付款，等待平台确认库存 |
| `confirmed` | 已确认，服务已安排 |
| `cancel_requested` | 取消申请中，正在与酒店核实 |
| `cancelled` | 已取消；退款中 / 已退款分别展示 |
| `completed` | 已完成 |

## 九、验收

1. 行程页中，可预订酒店显示「可预订 ¥x/晚」，售罄显示「已售罄」，无商品显示「参考价 ¥y · 本平台暂不提供预订」。
2. 第一期酒店与门票都会出现「可预订」；用车不出现（行程里没有对应条目）。
3. 无可订项的行程：底部不显示选择入口，显示说明文案。
4. 加购页住宿按入住/退房日显示晚数、门票按出行人数给建议数量；可改间数或票数，小计与合计随输入实时更新。
5. 加购页单价与价库一致；行程生成后价格变动时显示新价并提示「价格已更新」。
6. 提交时某项已售罄 → 409 返回逐项原因，前端标红对应项并刷新，不生成订单。
7. 相同 `Idempotency-Key` 重复提交 → 返回同一订单。
8. 下单成功 → 订单 `pending_payment`，收银页显示 15 分钟倒计时。
9. 模拟支付成功 → 订单 `paid_pending_review`，页面显示「已付款，等待平台确认库存」；不生成履约任务。
10. 模拟支付产生模拟积分（金额 // 10，`mock` 标识），会员中心与真实积分分开显示；清理脚本可按标识删除。
11. 全部不勾选 → 无法提交，不产生订单。
12. 他人行程的 `/checkout/:tripId` → 404；游客访问运营入口 → 403。

### 实现中发现并修复的问题：酒店节点丢失可售信息

**现象。** 用户说「想去北京，1 天」、未指定酒店时，规划出来的酒店（例如「北京如家精选故宫店」）是我们库存里的，但卡片没有可订标记，加购清单里也不出现。

**原因。** 景点节点在 LLM 筛选后会调用 `with_poi_identity` 把检索结果的身份与 `offer` 接回来；酒店节点没有这一步，LLM 返回的酒店列表直接落库，`offer` 与 `content_id` 全部丢失。加购清单只认带 `offer` 的条目，于是这家酒店被当成「仅参考」。

**修复。**

- 酒店节点在 LLM 返回后统一走 `with_poi_identity(item, pois)`，按 POI 身份回填 `offer` 与 `content_id`。
- 节点内再按 `sellable` 做一次稳定排序，保证落库顺序也是可售优先（排序主逻辑仍在 `sellability.sort_candidates`）。
- 提示词补充：`offer.sellable = true` 的酒店在同等条件下优先推荐；模型不得编造或修改 `offer`。

**验收。**

1. 北京 1 天、未指定酒店时，规划的酒店带 `offer.sellable = true`，价格为价库售价而非参考价。
2. 该酒店出现在加购清单里并可提交订单。
3. 报价停售或售罄时，同一家酒店显示不可售且不进入清单。
4. 模型输出里没有的酒店不会凭空获得 `offer`。

**验证。**

- 检索层实测（北京、预算 500）：返回 3 家，均来自内容层且带 `offer`（鼓楼亚朵 500/剩 5、如家精选故宫 350/剩 5、速 8 雍和宫 260/剩 5）。
- 用「仅含名称」的模拟 LLM 输出调用 `with_poi_identity`，两家酒店都正确接回 `offer` 与 `content_id`。
- `Hotel` 模型与 `model_dump()` 均保留 `offer`，确认能传到编译产物。
- 未跑完整 LLM 规划复测，未在浏览器复看卡片。

### 实现中发现并修复的问题（第二轮）：可售信息在编译阶段再次丢失

**现象。** 第一轮修复后，加购清单仍然为空，且行程里显示"本次规划没有拿到我们的库存"。

**原因。** `offer` 从检索到落库要经过四道手，第一轮只修了第一道：

```
检索结果(有 offer) → 节点回填(LLM 输出) → state(有) → 编译回填(逐日计划) → 行程
       ✅              ✅ 已修            ✅          ❌ 仍是空的
```

两处具体缺陷：

1. 编译器重新映射景点时用了 `with_poi_identity(a, pois) if "source" not in a else a`——模型复述的条目已经带 `source`，于是被跳过，`offer` 不补。
2. 酒店的赋值是 `hotel = dp.get("hotel")`，直接取模型写进逐日计划的酒店，从未回查 `state["hotels"]`，所以永远没有 `offer`。

**修复。**

- 景点：去掉 `"source" not in a` 这个捷径，每条都重新映射（`with_poi_identity` 幂等）。
- 酒店：新增 `_attach_hotel_offer(hotel, known)`，按名称回到 `state["hotels"]` 里找，命中就补 `id`、`content_id`、`offer`、`area`。
- 顺带修掉 `with_poi_identity` 里"模型把 id 原样抄回时提前返回、不复制 offer"的分支。

**验收。**

1. 行程里的酒店与景点带 `offer`，加购清单能列出并可勾选。
2. 清单显示价库售价（如 350、500 元）与剩余数量（剩 5）。
3. 勾选后可提交订单，跳转「我的订单」并完成模拟支付。
4. 检索确实为空时，行程出现「本次未检索到可预订库存」提示，加购页显示"没有拿到库存"而不是"未绑定商品"。

**验证。**

- 单元级：`_attach_hotel_offer({"name": "北京鼓楼亚朵酒店"}, known)` 返回带 `offer` 的字典；`with_poi_identity` 对"只给名字"和"抄回 id"两种情况都能补上 `offer`。
- 端到端（浏览器，用户验收）：加购页出现两家酒店 `2026-12-05 ¥350 剩 5`、`2026-12-06 ¥500 剩 5`，可勾选、可提交。

**复盘。** 同一个字段被两处逻辑丢弃，第一轮只覆盖了节点层。这类"回填"问题应该一次性把链路每一段都检查一遍，而不是修一处测一处。
