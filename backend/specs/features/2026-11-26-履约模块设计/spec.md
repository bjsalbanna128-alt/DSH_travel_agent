# 履约模块设计 · 运营确认后的任务与人车调度

任务开始日期 2026-11-26 ｜ 功能迭代 ｜ 基于现有交易与车队代码修订，履约功能待实现

## 1. 何时进入履约

当前工作树已包含酒店、门票、独立接机和全天包车的模拟交易，以及北京车队的车型、车辆、司机和时段占用。运营确认订单表示供应商能够提供约定服务；酒店是否取得房号或确认号、门票是否出票、哪辆车和哪名司机执行，分别由履约任务记录。模拟任务只供项目内运营演示，不触发外部供应商订房、出票或派单。

**生成入口。** `services/orders.py::approve_order` 在同一事务内核对商品库存、确认用车的时段占用、更新订单并写入 `OrderEvent(kind="confirmed")`。复用这条已提交的业务流水，新增履约侧的持久处理记录（确认事件 ID 唯一，记录处理结果、失败原因和下次重试时间）。扫描已提交的确认事件并按订单幂等补建任务；周期工作可接入已有后台维护生命周期。已存在的是订单流水，事件消费、失败重试与履约任务仍需实施。确认接口成功后能查到“待生成 / 已生成 / 需核实”，不要求运营再确认一次订单。

**生成守卫。** 锁定订单后核对 `status=confirmed`、`fund_status=paid`、模拟支付成功记录与确认流水，按冻结的 `OrderItem.id` 逐项核对。整单创建缺失任务、创建流水、标记处理成功在同一事务完成。已取消/已完成跳过；`cancel_requested` 暂缓，回到 confirmed 后重新检查，即使没有第二条 confirmed 事件也能恢复。重复消费只补缺项，不重置已经执行的任务。历史单满足相同证据且仍待执行时才补建；服务日期已过且执行情况未知、用车快照残缺、占用对不上时进入运营核实清单。免费行程、未支付、已付待复核和被拒订单均不生成任务。

本期交付任务与凭证、手工派车、异常处理、今日及未来七天看板。路书履约投影已有单独设计，本轮以订单项目为关联依据，提供后续读取所需的状态及实际时间。现有订单项目未统一保存投影设计所述的 `source_ref`；不能靠路书名称反推任务。本轮不增加游客路书叠加、自动派单、司机端或 GPS。

## 2. 模型

### 2.1 `fulfillment_tasks` — 履约任务

| 字段 | 类型与约束 | 含义 |
|---|---|---|
| `id` | String(36) PK | |
| `order_id` | FK `orders.id` ON DELETE RESTRICT，索引 | 来源订单 |
| `order_item_id` | FK `order_items.id` ON DELETE RESTRICT，**唯一** | 一个执行项目对应一个任务；每趟用车须独立成行 |
| `user_id` | String(36) 可空 | 游客，散客单为空 |
| `task_type` | String(24) 非空，`ck_ft_type` | `hotel_checkin` / `ticket_entry` / `vehicle_pickup` / `vehicle_charter` |
| `service_date` | Date 非空，索引 | 服务日期 |
| `planned_start_at` / `planned_end_at` | 带时区时间，可空 | 用车取冻结的完整起止时刻，按北京时间展示；酒店/门票只有日期时保持为空 |
| `started_at` / `completed_at` | 带时区时间，可空 | 实际开始、完成时由服务端写入，异常、恢复及撤销申请均保留已发生的事实 |
| `location_name` | String(160) 默认 `""` | 地点名（机场/酒店/景区） |
| `location_lat` / `location_lng` | Float 可空 | 坐标，来自商品 POI（可空） |
| `quantity` | Integer 非空，≥1 | 间夜/张/趟 |
| `contact_name` / `contact_phone` | 按权限只读引用 | 通过订单快照按需取联系人，默认脱敏，不重复保存明文 |
| `supplier_id` | String(36) 可空 | 履约方 |
| `supplier_name` | String(160) 默认 `""` | 生成时读取的显示名；用车优先取冻结名称，房票若从台账补显示名应注明来源 |
| `status` | String(16) 非空，`ck_ft_status` | 见第 3 节 |
| `voucher_no` | String(64) 默认 `""` | 单张凭证的展示值；多凭证及覆盖数量按本节下述明细存储 |
| `confirmation_no` | String(64) 默认 `""` | 供应商确认号 |
| `notes` | Text 默认 `""` | 运营备注 |
| `exception_reason` | Text 可空 | 异常原因 |
| `version` | Integer 非空，默认 1 | 乐观锁修订号 |
| `created_at` / `updated_at` | DateTime 非空 | |

索引：`ix_ft_date_status(service_date, status)`、`ix_ft_order(order_id)`、`ix_ft_supplier(supplier_id)`。

### 2.2 `dispatch_assignments` — 调度指派

| 字段 | 类型与约束 | 含义 |
|---|---|---|
| `id` | String(36) PK | |
| `task_id` | FK `fulfillment_tasks.id` ON DELETE RESTRICT，索引 | 同一任务可保留多次指派历史 |
| `vehicle_id` | FK `vehicles.id` ON DELETE RESTRICT，非空 | 车辆 |
| `driver_id` | FK `drivers.id` ON DELETE RESTRICT，非空 | 司机 |
| `assigned_by` / `assigned_by_name` | String(36) / String(50) 非空 | 指派人与姓名 |
| `assigned_at` | DateTime 非空 | |
| `released_at` | DateTime 可空 | 释放时间；非空表示历史指派 |
| `notes` | Text 默认 `""` | |

约束：`vehicle` 与 `driver` **必须属于同一车队供应商**（跨车队混派涉及责任划分，本期不允许）。按 task_id 对 released_at 为空的记录建立条件唯一约束。释放写 released_at，下一次指派新增一行。历史记录始终保留。

**从订单项目生成任务。**

| 冻结来源 | 任务与数量 | 核对依据 |
| --- | --- | --- |
| `hotel_room` | 每条逐日房晚项目一个 hotel_checkin 任务，数量为当晚房间数。两间住两晚产生两个任务，每个数量 2。 | 取项目服务日和房型；连续入住可用同一供应商确认号分别登记各晚覆盖数量。 |
| `attraction_ticket` | 每个服务日的票种项目一个 ticket_entry 任务，数量为张数。 | 凭证明细记录凭证及覆盖数量，或由运营登记覆盖整项数量的统一确认号。去重后数量覆盖全部才可就绪；部分出票留在 pending。凭证全文限获授权的详情读取，事件仅记摘要。 |
| `vehicle` | 每个项目一趟。读取 `attributes["fleet"]["purpose"]`，airport_transfer 生成 vehicle_pickup，charter 生成 vehicle_charter。 | 以项目 ID 关联 `FleetAllocation`，核实已确认的占用与冻结的 service_key、supplier_id、model_code、starts_at、ends_at、passengers、luggage 一致。详情从快照展示 pickup、dropoff、legs、车型和供应商；包车的一段路线不另建任务。 |

服务日期、商品、用车路线、时段和金额以冻结项目为准。房票的项目已有 supplier_id、product_name，供应商名称不是通用的订单项目快照字段。台账改名时不改历史任务。通过结构化凭证明细保存数量，写实际执行时间并保留异常前态，避免靠备注判断能否开始、退款或完成订单。

## 3. 任务状态与订单联动

| 动作 | 前提与结果 |
| --- | --- |
| 生成 | 订单已收款且已通过复核。酒店、门票任务按已确认的项目和服务日生成，车辆按每趟一条生成。初态 pending。 |
| 酒店/门票登记凭证 | 运营录入供应商确认号或足量凭证后 pending → ready。订单层的运营复核记录说明资源已核实，任务记录说明该服务已取得哪些凭证。 |
| 派车与撤派 | 用车时间地点完整，车辆和司机满足匹配与容量，派车成功 pending → ready。开始前撤派清除具体车与司机并回到 pending，继续保留本单已确认的时段容量；换车保留旧指派历史。 |
| 开始与完成 | ready → in_progress → completed。开始时再次核对订单可执行、凭证或有效指派。完成保留原始记录；运营完成订单时，须核对所有冻结项目已有任务、无待核实缺项，全部任务均已完成或有依据作废，且至少一项实际完成。零任务或仅已生成的部分任务全部结束时不能关单。 |
| 异常与恢复 | 非终态可登记原因进入 exception；恢复时回看前态并重新检查指派/凭证，条件失效则回 pending。异常状态也能按取消流程作废。 |
| 取消与退款 | 待复核时游客直接取消全退，始终无履约任务；酒店已确认、未入住时申请取消，等待运营核实供应商退订，期间阻止开始任务。正式取消后作废未完成任务并释放有效指派；进行中服务须人工核实已执行部分并记录原因，已完成项保留历史。全部作废走取消；部分已履行按订单规格 D4 处理，不能自动全退。资金结果由订单系统更新。 |

**与现有退订接口衔接。** 游客申请沿用 `request_cancel`，运营核实沿用 `resolve_cancel_request`。对任何品类，任务已开始、已完成，或异常前已有 started_at，均属于已有执行证据；在同一个订单锁下复查，不能被运营传入的 unused 覆盖。已使用复用现有订单退订售后工单，未知继续核实。核实全部未用并同意退订时，在现有取消事务内关闭任务、结束指派，与现有商品及车队占用释放一起提交。驳回后恢复原有任务，不重复生成。等待退订时暂停新派车、换车和开始动作。已执行事实可据实记录；同一订单不得同时全退并开工。单项异常本身不触发退款；任务作废记录业务依据，不能借作废绕过整单退订。

两端都不能借任务界面改订单商品、数量、日期、约定地点或金额。若游客要求改期，走原单适用的取消/售后流程，再按新库存另下单。运营可以在原服务约定内调整执行资源，不得以任务变动隐式替换订单。所有动作带版本；相同操作重试无重复事件，冲突返回 409。

## 4. 人车调度与预警

1. **一趟只有一份占用。** 销售侧已为每个用车项目保存一条 `fleet_allocations`，`order_item_id` 是主键，`vehicle_id/driver_id` 已预留。履约指派在原占用行填入这两个 ID，并写 `dispatch_assignments` 历史。两者同事务更新且必须相符；换车结束旧指派并建立新指派，撤派清空两个 ID。保持占用状态 confirmed；不重新调用销售预占，不递增报价的确认数量。订单正式取消统一由现有 `fleet_sales.release` 与库存服务处置。执行完成保留已消耗的日配额和原时段历史。
2. **固定这组人车后，其他订单也必须仍能履行。** 在订单锁和 `fleet_capacity.lock_fleets` 车队锁下读取 `roster/commitments`；把本任务原有 Demand **替换**为固定所选车和司机的 Demand，再用 `fits` 验证相关重叠链。不能调用表示新增需求的 `can_add` 来判断已确认任务能否指派。车队、启用状态、车辆型号、座位、行李容量、司机的服务城市和 `model_codes` 资格均为硬约束。即使具体人车当前无其他指派，若会使另一笔已承诺服务失去唯一合适司机，也应返回 409 并解释原因。换车同样核实，失败保留原指派。
3. **时间与并发。** 采用冻结起止时刻的左闭右开区间，统一 UTC 比较、北京时间展示；跨日查冲突，首尾相邻可接续。接机 120 分钟、包车 600 分钟已在销售端报价时计算，调度不能按当前默认值覆盖快照。沿用 SQLite 的写事务与现有订单→车队加锁顺序，多车队按固定顺序锁定，再核实任务版本、占用和台账。台账停用、改资格要看到已固定的人车；历史指派存在时删除返回 409。对超出约定结束时间仍在执行的车和司机标记异常，后续任务实际开始前核实上一任务已交车，避免计划时段相邻却重复出车。
4. **看板口径。** 今日、未来七天按服务日与车队筛选，跨午夜用车在相交的日期可见，同一任务在总数中去重。区分“销售已承诺”“已指派”“待派”“执行中”；已指派是承诺的一部分，不相加。现有 `GET /api/v1/admin/fleet/capacity` 表示可追加的时段余量，履约候选入口按第 2 条返回本任务可选的具体人车。异常看板显示缺凭证、临近未就绪、缺合适人车及超时执行；只有日期的任务不按零点报超时。付款后等待复核的 30 分钟提醒留在订单队列。

## 5. 接口、页面与交付顺序

在 `/api/v1/admin/fulfillment` 下提供任务列表、任务详情和时间线，以及凭证确认、指派、撤派、开始、完成、异常、恢复、作废动作；提供看板及资源可用时段查询。沿用运营鉴权、版本校验、分页与后台布局。详情显示订单号、服务约定、已确认供应商、任务状态，联系方式按操作场景授权读取，事件前后快照不含明文证件或电话。

在现有后台订单详情增加只读履约摘要与“完成订单”动作。当前订单模型支持 completed，订单路由尚无完成入口；新增运营写操作，使用订单锁、版本和第 3 节完成守卫，写订单状态及唯一完成流水。复用订单与工单服务处理全部作废和售后。第一步接通确认事件、房票任务与凭证，第二步接入现有北京车队台账和时段占用做手工指派，第三步验收取消、售后、完成和看板。后台车队台账、订单模拟支付和销售运力查询沿用现有实现。

## 6. 回归与验收

- 在 `backend/tests/test_fulfillment.py` 覆盖免费行程、未支付、已付待复核、复核拒绝四类均无任务；通过复核后生成，重复消费不重复，处理中断重试能补齐缺项。确认事件与取消乱序抵达也不产生可派的取消单。
- 同一订单两趟车能分别调度。跨午夜、两名运营同时派同车或同司机只成功一方；相邻无重叠时段成功。开始前撤派退回 pending、换车保留历史；时间未知、车不够坐、停用车辆均不能派。验证两趟错峰一辆车不报缺车，两趟重叠只有一名司机报缺司机。
- 酒店/门票缺凭证不能开始，异常可恢复或作废。退款成功不会二次释放车辆或商品库存。已开始或已完成的任务不能随请求退款被静默抹掉。旧订单数据迁移缺少可核实的模拟收款或复核证据时不自动开工。
- 前端从 `frontend/` 执行 `npm run build`，走查复核后任务出现、今日及未来七天、派车冲突、订单取消与历史凭证。首期支付独立验收也需验证履约未部署时确认事件可持久保存。
- 主要副作用为误派未确认订单、跨夜撞车、错误释放实际在用资源及旧订单重复派工。以上回归必须通过。D4 已确认开始服务后转人工售后，办理入住或履约开始记录要能供客服核实；D5 已确认后续用车的时段运力要求。自动派单、司机端联系范围后续立项时再定。

- 混合订单验收：两晚酒店、三张门票、首日接机和包车，逐项核对任务数与数量；两张票凭证不能让三张票就绪。模拟付款可正常演示，复核通过后才产生任务，不触发外部交易。
- 共享运力验收：最后一组人车已由本单占用，可追加余量为零时仍能给本单指派。双车型司机若是另一订单唯一候选，本次错误选择须失败。换车失败保留旧指派，撤派后不增加可售容量；已指派车辆或司机的停用、删除有保护。
- 恢复及完成验收：重复消费确认事件、暂缓后驳回取消申请、生成事务故障后重放、生成与取消并发、部分任务缺失时尝试完成、已经开始接机却申报全单未用。逐项检查任务状态、人车占用、库存、工单与退款流水。
- 数据库初始化纳入现有模型注册与升级检查，旧库重复升级不改订单、快照与既有占用。在隔离库回归 `test_fleet.py`、`test_orders.py`、`test_stock.py` 和新增履约测试；补游客与运营权限、任务重试及版本冲突用例。
