# 订单管理 · 游客下单支付与运营库存复核

任务开始日期 2026-11-26 ｜ 功能迭代 ｜ 先交付最小交易闭环，待实现

## 1. 已明确的规则与交付范围

1. 免费规划与付费增值服务分层。确认行程不等于购买服务。游客另选企业有供应商、有可售报价、有实际库存的商品后才建单。
2. 游客提交即冻结订单内容。C、B 两端都不能增删项目、改日期、换游客、改地址、议价或改成本。需要变化时走取消及适用的退款流程，再按当时库存和价格新下单。付款、复核、取消、退款、履约各自有留痕动作。
3. 已付款先进入“待运营确认”。运营根据本单占用及供应商实际供给复核整单；确认通过才具备履约资格。支付成功页面明确告诉游客还在等待确认。
4. 第一期开放**酒店房型与景点门票**，交付游客选房/选票、逐晚与逐张报价、下单、模拟收银、订单列表/详情及取消退款状态，运营仅需待确认列表、只读明细、通过/拒绝、取消申请处理和退款异常处理入口。用车不开放销售。完整 B 端管理和履约排在此闭环验收之后。

**演示样例。** 某酒店连续两天各有 1 间房。游客选 1 间住两晚，按两晚报价之和下单，看到倒计时。支付成功后显示“已付款，待运营确认”。运营看到两晚均由本单占用，向供应商核实后确认，游客刷新可见结果。另测一次第二晚供应商拒绝的情况：整单取消，游客持续看到退款进度，后台能追到拒绝、退款、库存处理各自的记录。

## 2. 订单和资金分别记录

| 当前服务状态 | 触发动作 | 结果与守卫 |
| --- | --- | --- |
| 待支付 pending_payment | 认证游客提交并成功预占 | 只允许本人支付或取消。请求响应丢失时查询服务端记录，不以浏览器按钮或页面跳转作为成功依据。 |
| 待支付 | 服务端核实全额支付成功 | 原子写模拟收款流水、模拟资金状态及订单事件，服务状态转为 paid_pending_review。此时不生成任务。 |
| 待支付 | 游客取消或支付超时且确认未收款 | cancelled，释放预占，资金为未收款，无退款单。 |
| 已付款待运营确认 paid_pending_review | 运营通过或拒绝 | 通过须逐项核实日期、数量、供应商可履约及本单占用，记录操作人与时间；全部通过才转 confirmed。任一项不能供给，记录明确原因，整单取消并建立全额退款义务。不能擅自替换商品。 |
| 已付款待运营确认 | 游客取消 | 整单取消，建立同一笔全额退款义务。与运营确认/拒绝发生竞争时以事务结果为准，失败方刷新并按最新状态处理。 |
| 已确认 confirmed | 游客申请取消 | 未开始时转 cancel_requested 并冻结执行。运营向酒店核实退订成功后转 cancelled 并发起全额模拟退款；酒店回复待定时保持申请中。酒店无法退订须记原因并告知游客，转人工售后。已开始时直接转人工售后。 |
| 已确认 | 履约阶段完成 | 有实际完成的任务且全部任务均已完成或作废才可 completed；全作废走取消。交易首期在“运营已确认”验收，不提前标记服务完成。 |
| 已取消 cancelled / 已完成 completed | 查询与后续资金处理 | 订单内容保持冻结。取消后仍可履行退款义务、重试或对账；退还上限为实收减已退、减正在处理的退款。 |

资金至少区分未收款、支付处理中、已收款、退款中、已退款、退款失败待重试。取消服务与到账是两个时间点，游客详情同时展示；运营拒绝原因面向游客，内部凭证单独保存。首期按整单一次性模拟付款，符合全退条件时按原模拟实收全额退还。收银、详情、退款结果及运营流水均标注“模拟支付／模拟退款”，部分退款与真实账务留待后续。

## 3. 第一阶段怎么实现

**游客页面。** 已登录游客可从可订酒店入口选择房型、入住日、退房日、间数和联系人，也可从可订门票入口选择票种、游览日和张数；两者都可选关联本人行程。退房日晚于入住日，入住日与游览日不得早于当前北京时间业务日。**用车保留后台资源管理，首期游客列表不返回，直接提交用车商品也应拒绝。** 提交前可编辑；提交后只读，展示订单号、商品快照、服务日、逐项金额、应付总额和状态。报价变化时要求按新价重新确认，不能静默加价。收银页显示实际支付模式与最终结果，订单详情在支付及退款处理中可刷新查询，离开页面、重新登录仍能查到订单。

**接口边界。** 在现有 FastAPI 鉴权体系下提供游客可售查询、`POST /api/v1/orders`、列表、本人详情、支付发起、取消或申请取消。会话提供游客身份，跨账号读取或操作其他订单不得成功。服务端按商品、服务日校验价格与库存，拒绝客户端传入金额覆盖、订单所有者覆盖或改项目。免费行程关联 ID 如有，校验归属。运营在 `/api/v1/admin/orders` 下获得复核队列、详情、确认/拒绝和退款跟踪；两端均不提供订单内容 PATCH。模拟收款与退款结果以本地服务端交易流水为准。

**模型与快照。** 使用 orders、order_items、order_travelers、order_events、支付与退款记录及按日的订单号序号。订单号沿用 ZY＋北京时间建单日＋流水号，数据库唯一。保存游客、可选单一行程、订单状态、资金状态、到期时间、版本、复核人与时间。项目保存商品与供应商 ID、名称/规格、日期、数量、成交单价与成本快照。金额以分记录，日期按业务日。客服读取历史价格不依赖当前价库。证件、电话沿用会员隐私机制，明细按权限脱敏，审计不复制敏感明文。新建、预占、快照、流水同一事务，重复点击以本人的同一提交键返回原单。支付中的多个尝试最多有一次有效收款，不允许双扣。

**复核与取消。** 后端检查本单的逐日占用，再让运营记录供应商核对结果、依据和原因。新查询到的“公共剩余数”不包含本单，不能用它作第二次扣减。通过、拒绝、游客取消与超时处理使用版本或条件更新；同一动作重放无重复副作用。确认事务内把占用转为确认占用，同时记录可重放的订单确认事件。拒绝或付后取消事务内落订单事件、库存处置及唯一待退款记录，由本地模拟退款处理器在提交后执行，可按原退款号恢复待办。库存释放条件见《履约模块前置修改》第 3 节。

**本地模拟收银。** 收银页显示订单号、酒店、服务日期、应付总额及“模拟支付，不会扣款”。游客点击“确认模拟付款”调用 `POST /api/v1/orders/{id}/payments`，携带请求幂等键。后端锁定本人的订单，取冻结金额，按服务端时钟校验仍在支付窗口内，写入 `provider=mock` 的唯一成功流水并转待复核，返回可查询的流水号。“返回订单”保留剩余支付时间。正常点击直接成功；测试可通过注入本地适配器失败结果验证重试，游客不能指定金额或交易结果。全流程不采集银行卡、支付密码，不依赖外部回调或商户密钥。模拟流水仅供演示，不计入正式经营收款。**模拟支付按实收金额产生模拟积分**（金额 // 10），交易以 `mock` 标识区分，在会员中心与真实积分分开展示，并提供按标识清理的脚本；模拟积分不参与正式对账与真实权益结算。

**15 分钟边界。** 建单成功时按服务器时间保存 `expires_at = created_at + 15 分钟`。每次支付在取得订单锁后判断：当前时刻严格早于到期点才可付款；恰好到期或更晚则关闭未付单、释放各晚占用，并返回已过期状态。周期清理（建议每分钟）处理关闭页面的订单；可售查询或下单发现目标报价仍有过期待支付占用时及时回收，再判余量。支付、取消、到期使用同一互斥条件。若收款事务已经成功，即使成功响应丢失、稍后跨过到期点，也查询返回原成功流水；已付待复核的订单不受这 15 分钟影响。

**复核时钟。** 从模拟付款成功时起计等待时长，队列按最久等待优先。首版内部提醒阈值取 30 分钟，通过后端配置调整；达到阈值高亮“复核超时”，保留待复核状态，游客仍可直接取消全退。该阈值只用于运营提醒。

**酒店退订与人工售后。** 待复核点取消直接生成全额模拟退款。已确认订单应提供“申请取消”动作，运营登记酒店退订结果、经办人、时间、可告知游客的原因。以酒店确认已办理入住或已有实际服务开始记录作为服务已开始的依据；交易首期尚无履约模块，由复核人员核实并登记酒店答复。仅有入住日期或信息不明时保留待核实，避免把入住日凌晨当作已经入住。连住多晚且首晚已经入住，整单进入人工售后。游客可从订单详情进入现有客服工单入口，带入本人订单号；重复点击回到原工单。售后人员核实后回复处理结果，首期不自动计算已使用间夜的退款。

**模拟退款与恢复。** 整单建立一条退款记录，金额由服务端取原模拟实收。先展示“模拟退款中”，本地处理器按唯一退款号落成功流水后展示“模拟已退款”。失败保留待重试原因，后台可以重试，服务重启能继续处理未完记录。复核拒绝、重复取消、重试或刷新均不得导致两笔退款。

## 4. 分期及与履约交接

| 顺序 | 可独立验收的交付 |
| --- | --- |
| A. 资源准备 | 运营维护实际供应商、试点商品、逐日售价和库存。缺少任一条件不能购买。详见前置规格。 |
| B. 最小 C 端交易 + B 端复核 | 以本地酒店模拟收银完整走通正常、取消和拒绝三条路径。无需等完整订单后台和派车看板。 |
| C. 后台订单管理 | 在同一模型扩展运营订单列表、状态/日期/游客/单号筛选、明细、毛利、收退款流水、复核与处理时间线。代客建单/散客和导出可后续立项，订单冻结规则仍适用。 |
| D. 履约 | 消费已确认订单事件，生成酒店/门票/用车任务。上线时核对已确认且仍待执行的存量单并幂等补建；已取消、已履行或历史归属不明的单据单独核实。 |

## 5. 已确认的六项决策

| 编号 | 执行规则 |
| --- | --- |
| D1 支付 | 首期仅本地模拟收款与退款，不收真钱。真实渠道另行立项。 |
| D2 库存 | 提交酒店订单后逐晚预占 15 分钟。未付到期释放；付后保留本单占用供运营复核。 |
| D3 品类 | 首期游客可订**酒店房型与景点门票**。B 端维护真实供应商、房型/票种、按服务日的库存和人民币售价。用车不开放销售。 |
| D4 取消 | 待复核时游客直接取消全退；已确认、未开始时申请取消，运营核实酒店退订成功后全退；已开始服务转人工售后。 |
| D5 用车 | 后续开放时每趟一行，记录时间、上下车点和人数，开放销售前核实时段运力，运营复核前不承诺订妥。本次不交付用车销售或派车。 |
| D6 运营复核 | 队列显示等待时长、超时高亮，不自动拒单。30 分钟是可调整的首版提醒默认值，游客等待期间可直接取消全退。 |

### 偏离与未完成

- 订单出行人在配置了 `pii_encryption_key` 时保存证件密文（AES-GCM，上下文绑定订单与出行人序号），未配置时只保留掩码；接口始终只返回掩码。
- 复核超时阈值改为 `settings.order_review_alert_minutes`（默认 30），详情返回 `waiting_minutes`、`review_alert_minutes` 与 `review_overdue`；运营队列对超时单显示红色「复核超时」标签。
- 退款处理器支持按订单过滤：单笔取消/拒绝只处理本单退款，`sweep` 才处理全部待退款记录。
- 模拟积分清理脚本：`python -m scripts.clean_mock_points [--dry-run]`，按 `mock-` 前缀删除模拟流水与对应积分批次并重算余额。
- C 端「我的订单」与 B 端「订单复核」两个页面已实现（列表 + 详情抽屉 + 模拟支付 / 取消 / 申请取消 / 通过 / 拒绝 / 处置取消申请 / 清理按钮），但未做浏览器走查。
