# 消息管理与工单提醒

任务日期为 2026-11-25，状态为已实现。对应企业后台“消息管理／消息配置”与“客服售后／客服工单”，沿用单企业、多个同权运营账号。

## 一、目标与交付范围

游客确认行程后，运营在后台收到提醒。游客提交咨询、投诉或建议后，每位运营收到自己的工单提醒；首位成功接单的人负责答复，游客可以查看实际处理结果。企业运营人员可在配置页决定是否对之后发生的业务动作发送站内提醒。

个人收件箱记录“我读过什么”，工单记录“谁接手、何时接手、答复是什么”。打开一条提醒不会自动接单，也不会替其他运营标记已读。首页推荐弹窗与本功能独立。此次采用站内通知和前台轮询；外部渠道、工单附件、客服聊天、SLA 计时及订单绑定留待后续迭代。未绑定订单也可提交工单。

## 二、三个通知项与最小配置页

在后台增加“消息管理 → 消息配置”。下表即完整配置清单，三个开关默认开启，模板文案、触发条件、收件人和站内通道由系统内置。每名运营均可查看和修改企业级开关。

| 配置项／事件 | 何时触发 | 收件人 | 点击提醒后的效果 |
|---|---|---|---|
| 行程确认提醒运营 `trip.confirmed` | 游客的行程首次从待确认变为已确认 | 当时每名运营各一条 | 在后台查看确认摘要，含行程标题、行程 ID、确认版本和确认时间。保留原游客行程详情的归属校验。 |
| 新工单提醒运营 `ticket.created` | 游客成功创建工单 | 当时每名运营各一条 | 打开后台工单详情，读取最新负责人和处理状态。 |
| 工单处理完成提醒游客 `ticket.closed` | 负责人成功提交结果并关闭本轮工单 | 该工单的提交人一条 | 打开“我的工单”详情，定位此次完成记录及结果。 |

- 生成、保存或调整行程草稿产生零条提醒。游客确认行程只通知运营。接单、查看工单、改优先级或重开工单不额外生成通知。游客仍可在工单详情查看当前进度。
- 配置页显示通知名称、触发时机、收件范围、通道、启用状态及最近修改人和时间。保存成功后，以**业务事件发生时**的配置决定是否发送。关闭某项后，之前已经产生的消息和未读数保留；重新开启从新事件开始，不补发关闭期间的通知。系统重复启动保留运营保存的开关。
- 关闭通知只影响提醒。工单仍可提交、接单、关闭，游客随时可以从“我的工单”读取结果。配置保存失败时显示错误与服务端实际状态；不同运营同时改同一项时，用修订号防止旧页面覆盖新值。

## 三、个人消息列表、已读和高亮

C 端增加“我的消息”“我的工单”；B 端增加“我的消息”“消息配置”“工单”。每条已投递消息保存明确的收件人账号和身份。以运营 A、B 为例，同一业务事件生成两条独立消息。A 点开后仅 A 的记录有已读时间；即使 A 已处理完工单，B 的消息仍可显示未读。B 打开时看到的是工单当前状态。

1. 登录进入对应界面或切回可见窗口时，立即请求本人的未读数；停留在前台期间每 30 秒刷新一次。仅在消息列表页同步刷新列表，进入列表时立即拉取当前页。页面恢复焦点与定时刷新重合时合并请求。
2. 未读数大于零时，在消息入口显示高亮徽标和数量。列表按发送时间及 ID 倒序，未读行显示加粗标题和“未读”标识；成功刷新时即展示变化。浏览列表不会自动清空未读。已发送但未读的消息才计数。
3. 点击一条提醒时按该条消息 ID 标记已读；成功后立即更新本人的行样式与徽标，无需等下次轮询。重复点击幂等。标记失败时保留未读并可重试；消息已读与工单负责人互不影响。
4. 刷新失败保留上次成功的列表与计数，下个周期重试。页面隐藏时暂停，恢复可见时立即刷新。登出、角色或账号切换时清除旧缓存和计时器，丢弃旧账号延迟返回的响应。验收口径为“消息可读后，在前台页面的下一次成功轮询中显示”，不承诺断网或后台标签页在 30 秒内更新。

## 四、工单与可追溯的处理记录

游客按咨询、投诉或建议填写主题和内容，在自己的工单列表和详情中查看状态、各轮完成时间及面向游客的处理说明。创建时服务端生成唯一工单号，提交人取当前登录账号，初始状态为 `new`、负责人为空、优先级为普通。保留可空订单字段，本期创建表单不收订单号。后台可按状态、分类、负责人筛选；优先级如需调整由运营设置。

| 操作 | 前置条件及执行人 | 状态变化与记录 |
|---|---|---|
| 开始处理 | 任一运营；工单处于 `new` 且无人接手 | 原子更新为 `processing`，负责人取当前账号；开始第 1 轮处理，记录工单 ID、轮次、处理人 ID、姓名快照及接单时间。 |
| 提交结果并关闭 | 工单处于 `processing`，仅当前负责人可操作；要求非空白、能回答游客问题的纯文本说明 | 在同一处理记录补充结果、完成时间及完成人；工单变为 `closed`。按“工单处理完成”配置通知游客。 |
| 重新打开 | 已关闭工单，任一运营主动点击“重新打开并处理” | 从 `closed` 进入 `processing`；重开者成为新一轮负责人，追加轮次与接手时间。前一轮的经手人、结果和时间保留。 |

运营打开同一张新工单时都能看见“开始处理”。服务端使用带状态、负责人和修订号条件的数据库更新，在同一事务内写入负责人和处理记录。并发接单仅一个成功，另一方得到 409 并刷新为“已由 A 处理”。签收后的写操作须核对负责人、状态和修订号，避免其他运营代填或旧页面关闭已重开的工单。其他运营仍可查看；页面按钮与服务端规则一致。

**验收示例。** 游客提交咨询“接驳车在哪里上车？”，生成 T001。A 接手后，后台显示“T001／第 1 轮／A／接单时间”。A 填写“请于 08:30 在酒店东门集合”并关闭后，同一行显示完成时间和这段答复；游客从自己的详情页看到答复。B 重开时新增“T001／第 2 轮／B”，第 1 轮仍可追溯。游客详情返回其有权查看的状态与各轮答复，内部账号 ID 只在后台展示。

## 五、存储、事件与失败恢复

沿用 FastAPI、SQLAlchemy 和当前数据库初始化方式。建议按下列职责组织新增表，旧库只增加本功能所需结构。

| 数据 | 核心字段和约束 |
|---|---|
| 通知配置 `message_settings` | 固定通知代码为主键、启用开关、修订号、修改人和修改时间。首次初始化补齐三个默认项。 |
| 工单 `tickets` | ID、唯一工单号、提交人 ID、可空订单 ID、分类、主题、内容、状态、优先级、当前负责人 ID、修订号及创建和更新时间。 |
| 处理记录 `ticket_handlings` | 工单 ID、轮次、处理人 ID 与显示名快照、接单时间、完成时间、完成人和处理结果。工单与轮次组合唯一，每张工单至多一轮进行中。 |
| 待投递事件 `notification_events` | 唯一业务事件键、通知项、关联对象 ID 与版本／轮次、发生时间、必要展示数据、接收账号快照及投递进度。事务中记录启用时产生的事件。 |
| 每人一条的消息 `messages` | 事件键、通知项、收件人角色及账号、受控的目标类型和 ID、标题、正文、发送状态、错误摘要、发送及已读时间。数据库保证“同一事件＋通知项＋收件账号”唯一。 |

- 行程 REST、SSE、WebSocket 共用 `planning_review.review_draft`。在确认状态成功写入的**同一业务事务**中，仅当 `newly_confirmed` 为真才登记待投递事件；草稿保存路径不登记。工单创建和每轮关闭也在各自事务中登记。事件键分别包含首次确认的行程和版本、创建的工单、关闭的工单和轮次；同一轮重试只发一次，第二轮真正关闭时可以再发。
- 事务提交后由投递任务按快照生成个人消息；服务启动及运行期间扫描未完成事件并重试暂时性失败。普通路径在提交后及时触发投递。投递或模板渲染失败不会撤销已确认的行程或已提交的工单。若连业务事务本身都无法持久化，接口按失败处理，避免声称业务已成功但遗漏待发事件。
- 内置模板渲染时检查占位符，缺变量则记录失败原因，失败记录不进入收件箱。部分收件人已成功时，重试借助唯一约束跳过已有成功消息；失败记录修复后更新原记录。已读时间仅写首次成功标记的时间。列表和计数使用相同收件角色、账号及成功状态过滤条件。
- 在已有 SQLite 和配置支持的 PostgreSQL 上遵守相同唯一约束和事务语义。轮询查询按收件角色、账号、发送状态及发送时间建索引；工单按提交人、状态及负责人检索。现有用户和行程无需补发历史消息。

## 六、接口、权限与实施顺序

以下为相对 `/api/v1` 的路径。游客接口复用现有登录依赖和账号归属校验，后台接口挂入 `require_operator` 路由组。身份、处理人、提交人取服务端认证结果。列表均支持稳定排序、分页与总数。

| 接口 | 行为 |
|---|---|
| 游客 `/messages`、运营 `/admin/messages` | 各自前缀提供 GET 列表（含 `unread_only`）、GET `/unread-count`、GET `/{id}` 详情和 POST `/{id}/read`。只操作自己的消息副本。 |
| `GET /admin/message-settings`、`PATCH /admin/message-settings/{code}` | 列出三个内置项，按预期修订号修改单项启用状态。 |
| `POST /tickets`、`GET /tickets`、`GET /tickets/{id}` | 提交工单、分页查看自己的工单、查看详情及各轮结果。 |
| `GET /admin/tickets`、`GET /admin/tickets/{id}` | 企业工单列表、详情和处理记录。 |
| `POST /admin/tickets/{id}/claim`、`/close`、`/reopen` | 三个动作均以该工单路径为前缀，按修订号接单、提交结果并关闭、重新打开并接手。关闭请求包含结果。 |
| `PATCH /admin/tickets/{id}/priority` | 运营按修订号设置低、普通或高优先级。 |

消息链接由前端按允许的目标类型构造。点击行程确认提醒进入本人的后台消息摘要；工单提醒进入有权查看的工单详情。未登录返回 401，游客请求后台或非负责人尝试关闭他人正在处理的工单返回 403，读取其他账号的私人消息或游客工单返回 404，状态或修订冲突返回 409，无效分类或空结果返回 422。

实施顺序为配置与持久化 → 个人收件箱和确认事件 → 工单及处理记录 → 两端页面和前台轮询。先验证权限、并发与幂等，再进行多账号界面联调。

## 验证记录

### 实现决定与影响

- 待投递事件随行程确认、工单创建或本轮关闭一起提交，配置和收件人取业务事件发生时的快照。服务提交后唤醒后台任务，任务也会在服务启动和运行期间扫描并重试未完成事件。
- 待接单的工单可由任一运营调整优先级，接单后由当前负责人调整。关闭后任一运营可以重开并接手，过去每轮的经手人、结果和完成时间会保留。工单号由服务端生成，后台与游客端均可见。
- 新增五张表并补齐三个默认配置，沿用现有数据库初始化流程。历史行程不补发提醒。完成记录和已投递通知会随业务量增加，由现有数据库一并保存。
- 消息页与导航共用当前账号的未读状态。停留在可见页面时每 30 秒请求未读数，只在收件箱页轮询列表。网络故障时保留本会话最后一次成功加载的结果。登出或切换身份时清理旧账号数据。

## 八、迭代记录：行程确认摘要补充信息

迭代日期 2026-11-25，状态已实现。

### 原因与目标

运营收到的「行程已确认」提醒，详情页只有行程标题、行程 ID、确认版本和确认时间，无法判断是哪个游客、去哪里、几天、多少钱，需要再跳到别处查。本次把确认摘要补成可以直接判断的信息。

### 范围与边界

- 摘要改为读取**确认版本的时间线快照**（`trip_versions` 中 `version = target_version` 的记录）取标题、目的地、天数、预估总费用，不再使用事件里保存的标题字符串；这是游客确认时看到的版本。
- 新增字段：游客账号（`member_id` + `username`）、目的地、天数、预估总费用、出行人数（取自 `travel_request.travelers`）、当前版本、`modified_after_confirm`（确认后是否被修改过）。
- 行程或快照缺失时逐字段回退到 `trips` 当前值，不报错。
- 运营从摘要页可跳转到「行程查询」详情页；游客侧不显示该入口。
- 通知模板与消息正文不变，信息只在详情页展示，列表页保持简洁。
- 不改动事件表结构与投递逻辑。

### 验收

1. 运营打开确认通知详情，能看到游客账号、目的地、天数、预估总费用、出行人数。
2. 游客确认后又编辑行程时，详情显示当前版本并标注「确认后已有修改」。
3. 行程或版本快照缺失时详情仍可打开，回退到行程当前值。
