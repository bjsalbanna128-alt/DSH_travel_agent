# 车队服务 · 北京试点供给与行程用车加购

任务开始日期 2026-11-26 ｜ 功能迭代 ｜ 已实现并完成本地验收

## 一、目标与交付边界

首版销售两种服务：**全天包车**（charter）和**独立接机**（airport_transfer）。游客在路书里能看到当天包车覆盖哪些酒店和景点，也能在首日单独选择接机。酒店到景点、景点到景点是包车覆盖的路段，首版不单卖这些路段。接站、送机、半天包车、跨城与异地还车留待后续。车队按行程移动需求匹配，沿用关系库中的供应商、商品、逐日报价与库存，无需进入地点内容库或向量检索。

本轮交付北京演示供给、运营人车台账、路书用车选项、加购、模拟支付与运营复核。订单确认后保留后续履约可读取的数据；具体指派车牌与司机、司机端、GPS 和派车单留到履约迭代。免费行程不占运力，游客可以只拿路书。

## 二、游客怎样选择服务

| 服务 | 游客看到什么 | 按什么收费 |
| --- | --- | --- |
| 全天包车 | 服务日期、约定起止时间、车型和可乘人数，以及按顺序列出的覆盖路段，例如“酒店 → 故宫 → 颐和园 → 酒店” | 约定时段内的整条游玩路线收一趟费用；路段数量不改变单价 |
| 独立接机 | 首日可主动添加“需要接机”，填写具体机场及航站楼（适用时）、上车时间、送达酒店或其他北京市内地点、乘客数与行李数 | 从约定机场到送达地点收一趟费用，与同日包车分别勾选、计价、占用 |

1. 编译阶段从已排定的酒店与景点序列取得覆盖路段，复用现有 `build_intraday_transports` 的路段逻辑。换酒店时按已知的实际起终点展示；缺失的站点或坐标不可凭空补全。累计距离 ≥8 km 或预计移动时间 ≥60 分钟时突出“推荐包车”。短途或只游一处也可主动选包车，只要有明确服务路线和可用供给。阈值仅影响推荐强度。
2. 已明确乘机到达时可突出接机并预填游客已提供的信息。只有出发城市、火车到达或交通方式未知时，不自动判为乘机。首日仍可主动添加；“北京机场”占位文字不能作为有效上车点。行李默认 0 件，可在加购页修改，无需在规划澄清阶段追问。
3. 原步行、地铁或打车方案继续可见。未勾选时用车售价仅供比较，不计入应付。勾选后只把所选服务售价计入订单，覆盖路段的打车估价不重复相加。纯接机显示“接机”标签。无车、无司机或报价停售时仍能正常看路书、订酒店和门票。

## 三、车型、商品与运营台账

| 数据 | 口径 |
| --- | --- |
| 车队 | 启用的 `suppliers.kind=vehicle_fleet`，服务城市为北京。车、司机及商品归属须由服务端核实。 |
| 车型 | 车队内使用稳定 `model_code`。车辆记录与两类商品均引用同一车型编码；显示名可改。用 `supplier_id + model_code` 汇总同车型资源。 |
| 商品 | 现有 `type=vehicle`，必填车型编码、车型名称、正整数 `passenger_capacity`、用途；行李容量为非负整数。乘客容量不含司机。接机与包车可以各自维护售价与停售状态。 |
| 车辆与司机 | 沿用 vehicles、drivers。车辆含车型编码、车牌、容量、状态；司机含服务城市、可服务车型或与车型匹配的驾驶资格、状态。只计入本车队可用且适合该服务的资源；同一名司机即使能开多种车型也只能同时承担一趟。 |
| 旧数据 | 服务端价格单位、前端表单及明细统一为“元/趟”，保留旧商品名称与容量。旧“元/车天”报价、缺用途或缺车型编码的数据供运营核对，补齐并确认按趟售价后方可销售。历史订单仍按原快照展示。 |

车型选择先过滤城市、用途、上下架、服务时段、报价、余量、人数和行李，再从可售车型中取最小乘客容量；容量相同依次按售价与稳定编码排序。游客可切换至其他满足条件的车型。分别提示超员、行李装不下、缺报价和时段已满。运营修改车型、停用车辆或司机前，如果会使既有有效占用无法兑现，提示受影响的订单并阻止造成缺口的普通操作，交由运营核实处理。

## 四、日报价和时段运力

1. 每个“用途商品 × 服务日”有独立的 `price_offers`，人民币分存储，`total_quantity` 是该商品当日最多可售趟数。接机与包车共享同车队的实体车辆和司机；两个商品各有余量，并不保证同一时段还能同时接两单。
2. 每项用车服务带开始和结束时刻，采用北京时间，区间含开始、不含结束。北京试点以接机 120 分钟、全天包车 600 分钟计算预计占用，并在加购时展示。可跨午夜，按开始日取售价和日配额，时段冲突须跨日期检查。尚未知开始时间时展示候选及待填字段，不宣称该时段可售。
3. 可售须同时满足当日商品余量、所选车型在整段内有车、同车队在整段内有合适的司机。以重叠时段的有效预占和确认占用核算，同时考虑同一订单里的多项选择。不同车型共用司机；同一时段要存在满足各车型资格的人员组合。按占用起止边界计算并发需求，不能把互相错峰的两趟简单求和。北京试点只计入已有台账的资源。
4. 在订单项目或关联的占用明细持久记录每项服务标识、车队、车型、开始结束时刻、订单项目及占用状态。复用现有商品日计数；两种占用在同一事务内成功或全部回滚。建单、释放、复核及会影响容量的台账写入使用一致锁顺序；按车队序列化时段核对，避免分别锁接机/包车商品时重复售出最后一名司机。相同请求重放只占用一次。此时无需给游客订单指定司机或车牌。
5. 未支付预占 15 分钟，到期或游客取消后释放；模拟付款成功后保留本单运力供运营复核。通过时把两种预占转为确认占用；拒绝或退订按既有订单规则分别处理退款与运力释放，已确认服务须核实可退订。报价页可提示投放量与台账规模差异；销售时必须通过时段校验。后台展示“日投放、预占、已确认、指定时段剩余”，实际派车数留给履约。

## 五、路书、报价与订单接口

- **行程。** 用 `day_plan.vehicle_offers[]` 保存独立服务候选，空列表兼容老行程。每项至少有稳定的 `service_key`（对应本行程、日序、用途）、用途、覆盖路段或起终点、建议时段、候选车型与推荐原因。一次包车只生成一项；第一天可同时有接机和包车。报价与余量属于查询时刻的信息，行程快照不能直接用于成交。
- **加购。** 扩展现有 `GET /api/v1/checkout/options` 的用车分组，沿用本人已确认行程和 `departure_date`。缺日期时游客直接在加购页选出发日。提供用车重新报价操作，接收服务标识、所选车型、时段、上下车点、乘客与行李，返回逐项可售原因、价格和服务端报价凭据。改日期、车型、时段或影响承接条件的信息后使旧凭据失效，等新报价再提交；不改原路书。
- **建单。** `POST /api/v1/orders` 增加 `kind=vehicle`。一条选择代表一趟，数量固定为 1，以服务标识区分同一天的多项。后端从本人行程重建可选服务，核对车队、车型、用途、人数、行李、上落点、日期、时段、报价凭据及共享运力。商品改价或已售罄时返回对应选项原因，跨房、票、车的订单整体回滚；前端保留选择，游客重新确认。不能仅扩展枚举后沿用房票的地点绑定分支。
- **订单快照。** 保存服务标识、用途、车队、车型编码与名称、日期、起止时刻、上下车点、覆盖路段、乘客数、行李数、成交金额与原价格单位。接机、包车分别显示在游客及运营详情。提交后双方均不得改订单内容。沿用模拟收银、待运营确认、取消及退款状态；后续履约可从已确认项目分别生成 pickup/charter 任务。
- **后台。** `/admin/fleet` 提供车辆、司机两个标签页。API 在 `/api/v1/admin/fleet/{vehicles,drivers}` 下列表/新增，按记录 ID 编辑、停用或删除，校验运营权限、归属及历史引用。已有历史指派的记录只可停用；车型编码有车辆或商品引用时不可删除。容量查询接受车队、车型和起止时刻。司机电话仅限运营业务使用，游客候选不返回司机个人信息。

本次扩展对应《履约模块前置修改》的存量车辆报价与时段核实、《订单管理》的可售品类与冻结快照，以及《C端售卖与加购》的候选和报价校验。酒店/门票继续沿用现有接口行为。《履约模块设计》的具体人车指派在后续实施。

## 六、北京演示种子

`backend/scripts/seed_beijing_fleet.py` 用固定业务标识创建一个演示车队，三种车型各两台车、共四名演示司机；司机服务城市为北京，预置能覆盖各试点车型的资格数据。每种车型分别创建接机、全天包车商品：

| 车型（可乘客／行李） | 接机一趟 | 全天包车一趟 | 每商品日投放上限 |
| --- | ---: | ---: | ---: |
| 5 座轿车（4 人／2 件） | ¥300 | ¥600 | 3 |
| 7 座商务（6 人／4 件） | ¥450 | ¥900 | 3 |
| 大巴（20 人／10 件） | ¥800 | ¥1500 | 3 |

成本按售价的 70% 生成。初次在空试点数据上从北京时间指定起始日连续生成 90 日，共 6 个商品、540 条报价。相同起始日重复运行新增 0 条；次日滚动运行只补新一天的 6 条。用虚构联系人、车牌及司机信息；不覆盖运营改价、停售、停用、预占或确认占用，不删除旧日记录。

## 七、开发与验收顺序

| 顺序 | 测试场景 | 可观察结果 |
| --- | --- | --- |
| 1. 种子与迁移 | 空库初始化、同日重跑、次日续跑、运营改价/停售后再跑；旧报价改单位 | 核对 1 个供应商、6 个商品、540 条初始报价、6 台车、4 名司机；旧车天报价核价前不能卖，历史快照可读。 |
| 2. 路书 | 北京首日 08:00 从首都机场 T3 到酒店，10:00 开始“酒店 → 故宫 → 颐和园 → 酒店”包车 | 首日两个独立选项，轿车两项全选合计 ¥900；只选包车 ¥600，不叠加打车估价。火车到达不默认勾选接机；短途有供给也可主动选。 |
| 3. 加购 | 无出发日、机场只填“北京机场”、改时段、行李从 2 件改为 3 件、2 人/6 人/超 20 人 | 缺信息不能提交，补齐后按新时段查价；轿车容量不足时显示可容纳的新车型及价格，超出所有车型时仍可购买房票。 |
| 4. 共享运力 | 同车型同一时段两台车都被包车占用，接机商品日配额仍有余；不同车型同时申请最后一名合适司机；跨午夜与首尾相接 | 已占满时不能再卖；最后一个共享名额只有一单成功；跨夜重叠可检出，首尾相接可以接续。重叠服务与错峰服务分别测试。 |
| 5. 订单 | 同日选接机与包车、混合房票车建单、最后一项不可售、重复提交、15 分钟到期、已付订单跨过到期点再复核 | 快照和金额逐项可核对；失败整单回滚，重试不重复占用；未付到期释放两种容量，已付保留，确认不二次扣减。 |
| 6. 运营及回归 | 停用供应商、改车型名、编辑车/司机影响已有承诺、不同车型资格、取消与退订 | 车型关联稳定，受影响时段不再新售，历史订单可读；退款结果不重复释放。游客端看不到司机资料，后台容量指标可与订单占用核对。 |

后端在 `backend/tests/test_fleet.py` 及既有库存、加购、订单用例中覆盖上述场景，使用可控时钟、隔离数据库，至少以两个并发建单请求验证共享司机上限。前端从 `frontend/` 执行 `npm run build`，用游客和运营两个账号实走“路书 → 加购选日/换车 → 模拟支付 → 复核”。行程未购买任何服务时仍应完整显示原路书。

## 八、验证记录

2026-11-26 已完成北京车队台账、路书候选、按趟报价、混合建单、模拟付款、复核和退订。存量报价保留原金额，运营核定按趟售价后才能参与销售。接机送达点支持行程中的北京地点、已发布的北京地点及明确包含北京市行政区的详细地址。

- 隔离 SQLite 用例验证了旧库迁移、种子同日重跑与次日续跑、车型与行李容量、跨夜和首尾相接、同车型车辆耗尽，以及不同车型的两个并发订单争抢同一名司机。整段匹配保证一辆车和一名司机各自能连续覆盖本趟。混合房票车订单覆盖凭据变更整单回滚、重复提交、未支付释放、已付款保留占用、确认和退款。
- 前端生产构建通过。浏览器使用隔离数据库中的游客及运营账号实际选日，分别购买 ¥300 的轿车接机和 ¥900 的商务包车，完成模拟支付和确认。后台对应商务包车当日投放 3 趟，已确认 1 趟。
- 并发验收在 SQLite 完成。当前本机 Docker 引擎未运行，PostgreSQL 并发暂未执行。
- 后端全量回归仍存在基线的 9 个失败，涉及 POI、对话澄清和交通编排。

演示种子已在隔离数据库验证。需要将其导入自己的演示库时，从后端目录运行 `python -m scripts.seed_beijing_fleet --start-date YYYY-MM-DD`。省略起始日时从北京时间当天起生成 90 日报价。
