# 随机行程模板起程

## 原因与目标

B 端已经能编写并发布行程模板，后端也只读接口可用（`GET /api/v1/itinerary-templates` 只返回 `visibility = 'published'`），但 C 端没有任何入口能看到它们。用户如果「没有想法」，只能自己想目的地和天数。

本次给 C 端加一条轻量入口：从聊天页进入随机模板浏览，挑中一个模板后补充少量信息，直接用它起一次规划。

目标：

- 聊天页提供「没有想法？试试随机旅行」入口，不影响正常聊天。
- 模板一次展示一个，可换、可返回、可确认。
- 确认模板后补充必要信息，然后走**现有规划流程**，产出可确认的草稿。
- 不做模板内容的结构转换，不新增后端写接口。

## 范围和边界

### 一、入口：首页与聊天页的输入框上方

在**首页**（`/`）的内嵌聊天输入框上方、以及 `/chat` 聊天页的输入框上方，各加一行入口「没有想法？试试随机旅行」，点击跳转模板页。

- 首页是绝大多数用户的实际起点，入口必须放在这里；`/chat` 同步加一份，保证从任一聊天入口进入都能看到。
- 不做常驻侧栏，避免改动两个页面的布局与移动端适配。
- 入口始终显示，不随对话状态隐藏。

### 二、模板页：一次一个

新路由 `/inspiration`，标记 `area: 'c'`（只有游客可进，沿用现有身份分区守卫）。

- 进入时拉取已发布模板，前端随机取一个展示；数据来源为现有只读列表接口，**不改后端**。
- 展示内容复用现有 `ItineraryTemplateContent` 组件（后台已在用）：标题、目的地、天数、标签、简介、逐日活动、贴士。
- 操作按钮：
  - **不满意？换一个**：从已加载集合中随机切换，保证与当前展示的不是同一条；集合只有 1 条时按钮禁用并提示「暂时只有这一个模板」。
  - **确认模板**：打开补充信息表单。
  - **返回**：回到聊天页。聊天历史与连接会丢失，已确认接受，不做状态提升。
- 空态：没有任何已发布模板时展示说明文案，不显示「换一个」。

### 三、补充信息表单

确认模板后弹出（或页面内展开）表单，用于补齐模板无法提供的字段：

| 字段 | 必填 | 缺省行为 |
|---|---|---|
| 出发城市 `departure_city` | **是** | 为空时不允许提交，提示「请填写出发城市」 |
| 出行人数 `travelers`（成人/儿童/老人） | 否 | 默认 1 名成人 |
| 总预算 `budget_total` | 否 | 默认 0，由规划流程自行估算 |

模板已提供的字段直接带入，不允许在表单里改：`destination`、`days`、`preferences`（取模板 `tags`）。

提交后组装规划请求并启动规划，然后跳转到现有规划页 `/plan`。

> 有意的不一致：出发城市只在模板流程里必填，聊天流程仍然不要求。理由是模板流程的行程主题与天数都已固定，城际交通缺失会让结果明显不完整；聊天流程保持现状以免增加阻碍。此差异记录在案，后续若要统一需单独决策。

### 四、起程：复用现有规划流程

- 复用 `POST /api/v1/trips/stream` 的预填充通道：请求体带 `travel_request` 时后端置 `skip_parse`，跳过解析直接进入规划。
- 组装的 `travel_request` 字段：`destination`、`days`、`preferences`（模板 tags）、`travelers`、`budget_total`、`departure_city`。
- `travel_time` 与 `pace` 不提供，走默认；`travel_time` 当前不参与规划。
- 规划产物为草稿（`status = draft`），落库后进入现有确认流程，不额外生成已完成行程。
- 前端复用现有 SSE 流式规划与 `PlanPage` 展示，不新建规划页。

### 五、非目标

- 不做模板内容的逐项落实：模板里的具体景点、餐厅、酒店**不会**成为行程条目；规划会按城市与偏好重新检索 POI。结果是「同城、同天数、同主题的新行程」。
- 不按名称反查 POI 补坐标。
- 不生成草稿以外的记录，不写模板使用次数。
- 不做常驻侧栏、不做模板收藏、不做分享。
- 不改造聊天页状态以保留历史（返回后历史丢失，已确认接受）。

### 六、可能受影响的现有行为

- 首页与聊天页各新增一行入口，布局有小幅变化。
- 新增一个 C 端路由，需标记 `area: 'c'`，否则游客会被身份分区守卫拦下。
- 规划入口多一条来源，`trips` 表新增记录的 `travel_request` 会带模板推导出的 `preferences`。
- 模板只读接口增加一类调用方，但仍要求登录。

## 验收

1. 游客登录后进入**首页**，输入框上方能看到「没有想法？试试随机旅行」入口，点击进入模板页；`/chat` 页同样可见。
2. 模板页展示一条已发布模板，包含标题、目的地、天数、标签、简介与逐日活动。
3. 有多条模板时「换一个」能切换，且不会连续显示同一条；只有一条时按钮禁用并给出提示。
4. 没有任何已发布模板时显示空态文案，不显示「换一个」。
5. 点「确认模板」出现补充信息表单；出发城市为空时无法提交并提示。
6. 填写出发城市后提交，进入规划页并在数十秒内生成草稿，草稿的目的地与天数与模板一致，`preferences` 含模板标签。
7. 草稿可走现有确认流程，确认后 `confirmed_version` 正常写入。
8. 「返回」回到聊天页；聊天历史清空属预期行为。
9. 未登录访问 `/inspiration` 跳转登录页；运营账号访问被守卫送回 `/admin`。

## 测试与回归计划

后端无需改动，不做新增接口测试。前端无自动化测试框架，本次采用构建 + 手工走查：

1. `npm run build` 通过。
2. 按验收 1–9 逐条手工验证，记录实际结果。
3. 回归：正常聊天规划、模板内容展示（后台预览）与既有 C 端路由不受影响。

若后续为该入口增加后端「随机模板」接口，再补对应后端用例。

## 已确认决策

1. 补充信息放确认模板之后的表单，而不是模板页底部常驻输入框。
2. 模板的 `tags` 直接作为 `preferences` 传入，不做偏好词映射。
3. 出发城市必填（仅限本流程）。

## 待定项

1. 入口卡片在聊天页的具体位置与文案细节，实现时按视觉走查调整。
2. 模板集合的加载量：默认一次取 20 条用于随机；模板增多后可改为后端随机。

## 验证记录

已实现。涉及文件：

- 前端：`views/InspirationPage.vue`（新增）、`views/ChatPage.vue`（输入框上方常驻入口）、`router/index.ts`（`/inspiration`，`area: 'c'`）、`api/itineraryTemplates.ts`（新增 `listPublished`）、`types/itineraryTemplates.ts`（新增 `ReaderTemplateSummary`）、`stores/travel.ts`（抽出 `startPlanningWithRequest` 并导出，`startPlanningWithClarifiedRequest` 改为调用它）
- 后端：无改动

已执行：

- **契约核对**：用游客身份实际请求只读接口，列表项字段与 `ReaderTemplateSummary` 完全一致（`id`、`version`、`title`、`destination`、`days_count`、`tags`、`description`、`published_at`）；详情额外含 `tips`、`days`，`days[].activities[]` 为 `time`/`name`/`category`/`description`/`product`，与 `ItineraryTemplateContent` 的入参一致。
- **预填充映射核对**：直接调用 `parse_request_node` 的 `skip_parse` 分支（不经过模型），输入模板推导的 `{destination, days, preferences, adults, children, elderly, budget_total, departure_city}`，得到 `destination=大理`、`days=3`、`budget={total_cny: 8000, per_day_cny: 2666.67}`、`travelers={adults: 2, children: 1, elderly: 0}`、`departure_city=北京`，字段全部正确落地。
- 前端 `npm run build` 通过（`vue-tsc` 类型检查 + vite 构建，712ms，仅既存 chunk 体积提示）。

观察到的数据问题（不属本次代码缺陷）：当前唯一模板的 `tags` 是「一人」。按已确认决策 tags 直接作为 `preferences` 传入，因此该模板会把「一人」当作偏好类型交给规划。模板录入时应使用偏好词（文化历史/自然风光/美食体验等），或后续单独做映射。
