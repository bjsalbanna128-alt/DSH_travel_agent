# 企业后台工作台 · 经营概览与待办预警

日期 2026-11-26 ｜ 分类 功能迭代 ｜ 状态 已实现

## 1. 改动原因、目标与边界

《旅游Agent工作内容清单》要求企业后台提供“经营概览、待办预警”。目前运营登录后进入 `/admin`，首页只有标题。运营要分别打开行程、会员、内容和工单等列表，才能知道企业有多少业务、哪些事需要自己处理。

本轮把现有后台首页做成运营的第一站。企业数据供所有运营查看，个人待办随登录账号变化。运营能从数字进入对应列表，或从高优先级工单直接进入详情。数据沿用单企业、多个同权运营的现有模型，开发和验收都可以用已有业务记录或测试数据完成，无需游客端配合开发。

交付范围为一个后台页面、一个只读聚合接口，以及支撑跳转的后台列表筛选。订单金额、收入、支付转化、超时规则和消息推送均留给相应业务迭代。工作台读取当前状态，接单、改优先级、关闭工单、阅读单条消息仍走各自已有的业务入口。本轮无需新增表、迁移、定时统计任务或外部依赖。

## 2. 页面与统计口径

### 2.1 经营概览

首页上半部分展示以下四张卡。主数字显示总数，辅助数字注明统计含义。点击整张卡进入对应的后台总列表，辅助数字仅展示。数据稳定时，主数字应等于目标列表清空筛选后的总条数。

| 卡片 | 主数字如何计算 | 辅助数字 | 点击后 |
| --- | --- | --- | --- |
| 已确认行程 | 沿用运营行程列表的可见范围，`Trip.status = completed` 且能关联到用户。按行程 ID 计一次，修改、确认新版本或回滚均不会让同一行程重复计数 | — | `/admin/trips` |
| 游客会员 | 当前角色为 `tourist` 的用户账号数。刚注册、尚未建立档案或没有消费的游客也计入 | 今日新增会员，按账号注册时间 | `/admin/members` |
| 行程模板 | 模板主记录总数，包含草稿、已发布、已下架 | 其中已发布，按主记录 `visibility = published` | `/admin/itinerary-templates` |
| 推荐内容 | 推荐主记录总数，包含草稿、已发布、已下架 | 其中已发布，口径同模板 | `/admin/recommendations` |

内容的已发布版本仍对游客可见时，运营编辑下一稿不应使已发布数减少。发布第二版也只计一份内容。今日新增单独标明对象，本轮展示“今日新增会员”和“今日新工单”。行程的最后更新时间会随编辑变化，不能作为确认时间统计。

### 2.2 待办与预警

下半部分用文字区分“全企业”和“我的”。在工单区域辅助展示“今日新工单”，按创建时间统计所有状态，接单或关单后仍计入当天新增。

| 入口 | 数字口径 | 点开后看到什么 |
| --- | --- | --- |
| 待接单（全企业） | `status = new` 且 `assignee_id IS NULL` | 工单列表，已选“待接单”和“未分配” |
| 我处理中 | `status = processing` 且负责人是当前运营 | 工单列表，状态为处理中，负责人为当前账号 |
| 高优先级待接单（全企业） | 待接单中 `priority = high` 的数量 | 工单列表，同时选中待接单、未分配、高优先级 |
| 我的未读消息 | 收件角色为运营、收件人为当前运营、发送状态为 `sent`、`read_at IS NULL` | 个人消息列表，已选“只看未读” |

高优先级待接单属于待接单的一部分，两者不相加。高优先级或未读数量大于零时，高亮相应入口并显示文字和数量。高优先级入口下最多列出 5 条，先展示创建最早的工单，同一创建时间按 ID 升序。每行展示工单编号、类别、创建时间，可直接打开 `/admin/tickets/:id`；入口数字始终是符合条件的全部数量。若已有其他运营接单，详情页按最新状态和已有并发规则处理。

## 3. 后端实现约定

1. 在现有运营路由下增加 `GET /api/v1/admin/dashboard`，复用运营鉴权与数据库会话。未登录返回 401，游客返回 403。个人统计的账号由服务端根据会话确定，接口不提供指定收件人或负责人的参数。
2. 建立工作台响应模型和查询服务。响应字段按下表固定，计数为非负整数。只返回页面会用到的字段，工单摘要无需游客联系方式、证件、工单正文或完整处理历史。

| 响应字段 | 内容 |
| --- | --- |
| `as_of` | 服务端此次统计时间，ISO 8601，含时区 |
| `overview` | `confirmed_trips`、`tourist_members`、`new_members_today`、`templates_total`、`templates_published`、`recommendations_total`、`recommendations_published` |
| `work` | `unassigned_tickets`、`my_processing_tickets`、`high_unassigned_tickets`、`my_unread_messages`、`new_tickets_today` |
| `high_priority_items` | 有序摘要数组。每项含 `id`、`number`、`category`、`created_at`。空队列返回空数组 |

3. 一次请求取一次业务时钟。“今日”采用北京时间（Asia/Shanghai）当天零点至次日零点的左闭右开区间，转 UTC 后分别按数据库列的时间类型绑定。游客注册时间目前以无时区 UTC 存储，工单创建列声明带时区。两个查询必须代表同一对时刻。
4. 在数据库执行计数和限量查询。同一张表的总数与子集可用条件聚合一次取得。行程沿用 `services/admin_trips.py` 的可见条件，未读数复用 `services/notifications.py` 已有查询。避免为计数调用分页接口、遍历所有记录或逐张工单查详情。若聚合查询失败，按项目错误约定返回失败，由页面提供重试。
5. 运营工单列表沿用现有 `status`、`assignee_id`（含 `unassigned`），增加选填 `priority=low|normal|high`，复用既有优先级枚举。所有条件取交集，分页总数与结果使用同一筛选。不传新参数时保持既有结果，越界值返回 422。

## 4. 前端实现约定

1. 在现有 `AdminHomePage.vue` 展示工作台，保留运营首页路由、布局、导航和登录后的落点。使用项目已有 Vue、TypeScript、Element Plus 及后台请求封装。顶部显示“经营概览”和最近一次成功更新时间，下面展示待办与高优先级工单。
2. 待接单入口使用 `/admin/tickets?status=new&assignee_id=unassigned`，高优先级入口追加 `priority=high`。“我处理中”使用 `status=processing` 和当前运营 ID。“我的未读消息”使用 `/admin/messages?unread_only=true`。运营列表首次进入以及同页 URL 条件变化时，都同步选中项并从第一页查询。手动清除条件后同步 URL；刷新、分享工单筛选链接和浏览器后退均能还原筛选。个人消息始终按打开链接的登录人查询。
3. 首次进入加载一次。页面可见期间每 30 秒更新一次，回到前台立即刷新，并提供手动刷新。合并同时触发的请求，在离开首页时清理定时器和在途请求。协调首页与现有未读徽标的刷新，复用当前账号的未读状态，同次刷新避免重复获取未读数。阅读单条消息后沿用现有已读更新流程，旧请求不得把数字覆盖回去。
4. 首次加载显示加载态；成功且确实无数据时卡片显示 0，摘要显示“暂无高优先级待接工单”。首次请求失败显示错误与重试。后台刷新失败时保留同账号上次成功的数字和时间，并标示“刷新失败”。退出、切换账号、权限失效时清除旧账号结果，沿用现有鉴权处理。

## 5. 副作用与回归范围

| 可能影响 | 实现与回归要求 |
| --- | --- |
| 运营和游客共用工单、收件箱组件 | 只给运营工单列表增加优先级筛选；验证游客原有列表、消息阅读及权限边界 |
| 首页自动刷新增加数据库读取 | 只在可见时轮询，使用汇总查询和有上限的摘要。切换路由、切换账号后检查请求和定时器 |
| 首页数字与明细在多人并发时有短暂时间差 | 标示更新时间，列表和详情打开时读最新状态。打开首页和列表均不应接单、标记已读或触发新提醒 |
| 多个运营使用同一浏览器 | 个人统计跟随会话，延迟返回的旧账号响应必须丢弃。运营 A 的已读与运营 B 的已读独立 |
