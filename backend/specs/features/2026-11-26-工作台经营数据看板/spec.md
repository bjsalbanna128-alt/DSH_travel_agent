# 工作台经营数据看板

任务开始日期 2026-11-26 ｜ 功能迭代 ｜ 在现有「工作台」首页增加经营数据的趋势图表与明细表。

## 一、原因与目标

现有工作台只有静态计数器：已确认行程、游客会员、行程模板、推荐内容、待办与预警。这些数字回答"现在有多少"，但回答不了运营每天真正关心的问题：

- 这几天卖得怎么样？在涨还是在跌？
- 哪一类卖得多（酒店、门票、用车）？
- 收了多少钱、退了多少？
- 接下几天的履约任务有多重、车队够不够？

目标：在首页工作台增加**经营数据**区块，用「趋势图 + 品类构成 + 明细表」回答上面四类问题，数据口径固定、可核对。

## 二、范围与边界

### 本次交付

1. 新增聚合接口 `GET /api/v1/admin/dashboard/trends?days=7|30`。
2. 首页新增「经营数据」区块：每日趋势折线图、品类构成图、近 N 天明细表。
3. 口径定义写入本规格，前端每个数字可回溯到定义。
4. 无数据、部分数据、接口失败三种状态的明确表现。

### 不在本次范围

- 自定义时间区间（只提供近 7 天 / 近 30 天两个快捷档）。
- 按供应商、按渠道、按城市拆分（当前只有北京在售，拆了没有信息量）。
- 导出 Excel / CSV。
- 同比环比、预测。
- 财务对账口径（结算金额、成本毛利只在规格里给定义，不在此次展示）。

### 可能影响的现有行为

- 首页首屏多一次接口请求：与 `/v1/admin/dashboard` 并行发起，任一失败不影响另一个区块。
- 工作台接口本身不变，避免并行开发的 AI 运营线冲突。

## 三、口径定义

时区统一**北京时间自然日**（`Asia/Shanghai` 00:00–24:00），存储时间为 UTC，查询时换算。

| 指标 | 定义 | 数据来源 |
|---|---|---|
| **收款** | 当日完成支付的订单金额之和 | `order_payments.paid_at` 落在当日，取 `amount_fen` |
| **退款** | 当日退款成功的金额之和 | `order_refunds.status='succeeded'` 且 `processed_at` 落在当日 |
| **净收款** | 收款 − 退款 | 上面两项相减 |
| **订单数** | 当日创建且已支付的订单数 | `order_payments` 按 `order_id` 去重 |
| **客单价** | 净收款 ÷ 订单数 | 订单数为 0 时返回 0，不返回 null |
| **品类金额** | 当日支付订单的明细金额，按品类汇总 | `order_items.product_type`：`hotel_room` / `attraction_ticket` / `vehicle` |
| **履约任务量** | 服务日当天的任务数（不含已作废） | `fulfillment_tasks.service_date`、`status != 'cancelled'` |
| **就绪率** | 已就绪及以上 ÷ 任务量 | `ready` + `in_progress` + `completed` 占比 |
| **车队利用率** | 当日已固定人车的用车任务数 ÷ 车队在用车辆数 | `fleet_allocations.vehicle_id` 非空、`starts_at` 落在当日；分母为 `vehicles.status='active'` |

三条必须写死的规则：

1. **收款按支付日归集，不按出发日**。订单 11-20 支付、12-05 出行，计入 11-20。
2. **退款冲减到退款成功当日**，不回改原支付日的历史数字；因此历史某天的净收款可能为负，展示时保留负值并标注。
3. **已支付但已全额退款的订单仍计入当日的"订单数"**，因为当日确实成交过；净收款那一栏会相应体现。

## 四、数据来源

只读现有表，不新增业务表。

| 表 | 用途 | 现有索引 |
|---|---|---|
| `orders` | 订单状态分布、客单价分母 | `ix_order_status_created` |
| `order_items` | 品类金额 | 无 `service_date` 索引，按 `order_id` 关联 |
| `order_payments` | 收款、订单数 | `uq_payment_order` |
| `order_refunds` | 退款 | `ix_refund_pending` |
| `fulfillment_tasks` | 履约任务量、就绪率 | `ix_ft_date_status` |
| `fleet_allocations` | 车队利用率分子 | `ix_fleet_allocation_interval` |
| `vehicles` | 利用率分母 | 按 `supplier_id` |

数据量按日聚合，试点规模（千级订单）无需新增索引；若 30 天查询明显变慢，再评估 `order_payments(paid_at)` 索引并单独记规格。

## 五、接口

```
GET /api/v1/admin/dashboard/trends?days=7
```

- `days` 只接受 `7` 或 `30`，其它值 422。
- 运营鉴权（`CurrentOperator`），关闭缓存（`no_store`）。
- 区间**含今日**：最近 N 个北京自然日，最后一天是今日（0 点至今的累计值）。
- 今日是**进行中的半天数据**，会随当天交易继续增长；渲染时把今日点与今日行标注为「进行中」，避免和历史日直接比较产生误读。
- 返回按日期升序的完整序列，**没有数据的日子补 0**（前端不处理空洞）。

响应：

```json
{
  "days": 7,
  "from": "2026-11-20",
  "to": "2026-11-26",
  "as_of": "2026-11-26T08:30:00Z",
  "today": "2026-11-26",
  "series": [
    {"date": "2026-11-20", "paid_fen": 128000, "refund_fen": 0, "net_fen": 128000,
     "orders": 3, "avg_order_fen": 42667,
     "fulfillment_total": 5, "fulfillment_ready": 3, "fleet_used": 1, "fleet_capacity": 6}
  ],
  "totals": {
    "paid_fen": 512000, "refund_fen": 30000, "net_fen": 482000,
    "orders": 12, "avg_order_fen": 40167, "fulfillment_total": 21, "fleet_used": 4
  },
  "by_category": [
    {"product_type": "hotel_room", "amount_fen": 350000},
    {"product_type": "attraction_ticket", "amount_fen": 42000},
    {"product_type": "vehicle", "amount_fen": 90000}
  ]
}
```

约定：

- 金额一律**分**（整数），前端负责换算与千分位。
- `by_category` 覆盖区间内全部已支付明细，未出现的品类不返回，前端按三种固定品类补齐为 0。
- `today` 供前端标注"进行中"的日期，服务端按北京时间给出，前端不自行推导。
- 字段命名与现有 `DashboardResponse` 一致（`as_of`、`fen` 后缀）。

## 六、前端展示

位置：首页「经营概览」与「待办与预警」之间，标题「经营数据」，右上角切换「近 7 天 / 近 30 天」。

| 区块 | 形式 | 内容 |
|---|---|---|
| 趋势 | 折线图（双线） | 每日收款、每日退款；横轴日期 |
| 品类构成 | 横向条形图 | 酒店 / 门票 / 用车金额与占比 |
| 关键数字 | 一行 4 个 | 净收款、订单数、客单价、就绪率 |
| 明细 | 表格 | 日期、收款、退款、订单数、履约任务量、车队占用 |

交互与状态：

- 切换档位时保留上一次数据并显示加载态，避免整块闪烁。
- **全部为 0**：显示「近 7 天还没有成交」的空状态，不画空折线。
- 部分为 0：正常画，折线允许贴底。
- 接口失败：区块内错误提示 + 「重试」按钮，不影响工作台上半部分的计数器。
- 金额展示：`¥1,280.00`；净收款为负时红色显示并带负号。
- **净收款为负时的说明**：明细表该行日期后加一个警示图标，悬停提示「当日退款大于收款」；折线图上该点的 tooltip 同样带这句话。文案固定，不改写为「异常」或「亏损」，因为它可能是正常的隔日退款。

## 七、图表实现方式：手写 SVG

前端不加任何图表依赖，用 SVG 手写两类图。

**工作量与范围**

| 图 | 实现要点 |
|---|---|
| 双线折线（收款 / 退款） | 一个 `<svg viewBox>`，横轴等分日期，纵轴按 `max(paid, refund)` 取整刻度（0、中点、上限）；两条 `<polyline>`；每个数据点一个 `<circle>` 带 `<title>` 做原生 tooltip；坐标轴文字用 `<text>` |
| 横向条形（品类） | 三个 `<rect>`，宽度按占比，左侧品类名，右侧金额与百分比 |
| 负值点 | 净收款为负的日期在折线下方标一个红色小三角，`<title>` 为提示文案 |

**硬性要求**

- 响应式：`viewBox` + `width: 100%`，窄屏不溢出，不出现横向滚动。
- 无数据：不发请求到 SVG 绘制分支，直接渲染空状态。
- 全部为 0：纵轴上限取 1，避免除零，折线贴底。
- 日期多（30 天）时横轴标签**隔天显示**，避免文字重叠。
- **今日点特殊处理**：最后一个数据点画成空心圆，`<title>` 为「进行中（当日累计）」，横轴该日标签加粗；明细表对应行加「进行中」标签。
- 颜色与现有后台一致（`--el-color-primary` 系），退款线用灰色虚线。
- 无障碍：SVG 加 `role="img"` 与 `aria-label`，明细表本身提供等价文本。

预计 150–200 行，放在 `src/components/BusinessTrendChart.vue` 与 `src/components/CategoryBars.vue` 两个组件里，页面只组装。

## 八、验收条件

1. 首页在「待办与预警」上方出现「经营数据」区块，默认显示近 7 天。
2. 切换档位后，图表与明细表同步变化，日期序列连续无空洞，**且最后一天是今天**。
3. 造一笔今日支付订单后刷新，今日收款与订单数各增加对应数值，客单价随之变化；今日的数据点与明细行标有「进行中」。
4. 对一笔已支付订单执行模拟退款成功后，退款日（今日）的退款金额增加、净收款相应减少。
5. 无支付数据的日期显示为 0，折线贴底而非断点；全部为 0 时纵轴上限为 1，不报除零。
6. 无任何成交时显示空状态文案，而不是空白图。
7. 接口 500 时区块显示错误与重试按钮，工作台计数器仍正常显示。
8. 品类金额之和等于区间收款总额（退款单独列示，不参与该等式）。
9. `days=15` 返回 422；未登录返回 401。
10. 北京时间边界正确：UTC 时间 2026-11-25 17:00 的支付归入北京时间 11-26。
11. 净收款为负的行与数据点，悬停提示「当日退款大于收款」。
12. 30 天档位下横轴标签隔天显示，窄屏（375px）无横向滚动。

## 十一、已确认决策

1. **图表用**手写 SVG，不引入任何图表库。
2. **不展示成本与毛利**：`total_cost_fen` / `unit_cost_fen` 已有，但毛利口径涉及退款冲减与供应商结算，本期不展示。
3. **不按供应商拆分**：当前只有北京在售，拆分没有信息量。
4. **「近 7 天 / 近 30 天」含今日**：最后一天是今日（0 点至今的累计值），今日点在图上与明细行均标注「进行中」，提醒这是半天数据。
5. **净收款为负需要说明**：明细行与折线点均给出「当日退款大于收款」的提示，不改写成「异常」或「亏损」。

## 十二、待定项

1. **毛利**：明确放到第二期，与结算一起做；届时需要先定义退款冲减成本的口径。
2. **按供应商拆分**：等北京之外的城市上线后再提。

2. 响应用 `serialization_alias` 输出 `from` / `to`（Python 保留字），已实测键名正确。
