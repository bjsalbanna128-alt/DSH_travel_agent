# 企业后台资源管理：供应商、商品与每日报价

任务开始日期为 2026-11-25。资源管理已实现，本地验收结果见文末。本规格承接企业后台清单中的“资源管理”和已完成的运营身份与后台入口。

## 目标与范围

运营应能完成一条完整流程：建一家供应商，录入它提供的房型、票种或车型，为指定服务日期录入成本与对客售价，在商品详情判断当天能否出售。使用单企业、多个同权运营账号。首版由运营手工维护人民币报价。

本次交付供应商与商品的增删改查、上下架、POI 绑定、每日报价维护和三个后台页面。合同附件和结算流程只预留可空引用字段。库存数量、锁库存、合同上传、结算审批、游客端核价页面、订单、行程模板和推荐内容属于其他迭代。本期“可售”表示运营规则允许销售，实际供应余量需要库存功能支持。

## 仓库基线

当前分支已有受 `require_operator` 统一保护的 `/api/v1/admin`、Vue 的 `/admin` 子路由和 `AdminLayout.vue`。当前 ORM 以及工作区默认 SQLite 库均只有用户、用户偏好、行程、行程版本四张业务表，未发现旧 `price_offers` 表。现有高德和 Chroma 检索结果带有兴趣点（POI）标识，它们的估价和游客已保存的路书属于独立数据源。

## 一、三层数据模型

供应商一对多关联商品，商品一对多关联每日报价。一个商品归属一个供应商。两家供应商即使提供同一酒店的同名房型，也分别建立商品，允许两套成本与售价。下面是本次约定的存储口径。

| 表 | 主要字段 | 约束和含义 |
|---|---|---|
| `suppliers` | `id`、供应商名称、结算主体名称、联系人与联系方式、备注、状态、`contract_attachment_ref`、`settlement_workflow_ref`、创建及更新时间 | 供应商名称和结算主体必填，主体相同可由表单预填。状态为启用或停用，默认启用。两个预留引用可空，首版不通过 API 写入。 |
| `products` | `id`、`supplier_id`、商品名、类型、城市、规格属性、POI 引用、上架状态、创建及更新时间 | 供应商外键必填。默认下架。类型固定为酒店房型、景点门票、用车车型之一。类型决定属性校验、表单和报价单位。 |
| `price_offers` | `product_id`、`service_date`、`cost_fen`、`sale_fen`、`status` | 商品与服务日期共同作为主键。成本和售价分别以人民币分的整数保存，均必填且非负。状态为可售或停售。无记录表示当天未报价。 |

供应商名称、商品类型、房型名称、POI、计价单位通过关联读取，不在报价表重复保存。报价以当地服务日期（年-月-日）为键。界面以元输入和显示两位小数，API 明确使用整分；拒绝负金额、小数分和无效日期。零元是有效金额。售价低于成本时给运营提示，允许保存促销价。

### 类型与 POI

| 类型值 | 商品示例 | 首版必填规格 | 一份报价的含义 |
|---|---|---|---|
| `hotel_room` | 春熙路某酒店·双床房含双早 | 房型名、可住人数、早餐说明 | 入住当日，一间一夜 |
| `attraction_ticket` | 某博物馆·成人票 | 票种名、适用人群 | 游览当日，一张票 |
| `vehicle` | 成都接送·七座商务车 | 车型名、可乘客数 | 服务当日，一辆一天 |

人数必须为正整数。类型属性可放在商品的 JSON 列，由 FastAPI 按枚举分别校验并生成明确的响应结构。车型首版采用按车天报价；如后续提供按趟接送，应将其作为独立计价规格。

一个商品最多绑定一个主要 POI；多个商品可绑定同一地点。商品存来源、来源内 ID、名称快照和城市，业务匹配使用“来源 + ID”。房型上架前必须关联酒店，门票上架前必须关联景点，车辆可选关联服务网点或接驳地点。允许运营先保存未绑定的下架商品。后台提供按城市、关键词、地点类型查询并选择的入口；从现有高德或本地种子数据适配时保留来源标识，缺少来源内 ID 的结果不可选。查询失败给出重试提示，编辑已有商品时保留原绑定。报价录入不依赖外部地图服务在线。

## 二、写入规则与可售判定

1. **增删改查。** 供应商支持新建、详情、编辑、筛选、停启用和删除。商品支持新建、详情、编辑、筛选、上下架和删除。名称只用于展示与检索，记录操作按 ID 执行。有关联商品的供应商、有关联报价的商品，删除时返回 409，并提示先处理哪些记录。空供应商和无报价商品可删除。后端事务和数据库外键共同防止出现孤立记录；SQLite 连接须实际启用外键检查。
2. **供应商和商品状态。** 停用供应商立即使其所有商品的报价失去实际可售资格，保留原商品及报价状态。重新启用后按现有下级状态重新计算。停用期间允许查阅、纠正资料和维护草稿，禁止新上架。商品下架后仍可查阅和维护其报价。
3. **商品身份。** 商品有关联报价时，变更供应商或类型会改变旧报价指向的交易对象或计价单位，此类修改返回 409。更换交易对象应新建商品；已有价格的上架商品如需换绑 POI，先下架，核对其报价后再上架。
4. **当天是否可售。** 同时满足“供应商启用、商品上架、当天有报价、该报价为可售”才返回实际可售。详情分别展示报价自身状态和实际可售结果，并说明未报价、供应商停用、商品下架或当日停售等原因。后台可以查看所有状态。
5. **单日与批量报价。** 新增时必须明确成本、售价与状态。单日编辑按商品与日期更新原记录，日期填错时删除错误记录再新增。批量填价按闭区间生成每日记录，默认遇已有日期即返回 409 及冲突日期，整批不写入；运营预览并明确选择“覆盖已有报价”后才更新冲突日。整批同事务提交。单日停售可恢复；删除报价后当天回到“未报价”。
6. **酒店跨夜核对。** 后台可按入住日到退房日前一日查看逐夜明细，各夜分别按当日价格计费。两晚中缺一晚或有停售时，标明具体日期及原因，整段不能显示为可售。该查询用于运营自查，成本只向运营展示。

## 三、后台接口与页面

沿用现有 Vue、Element Plus、FastAPI、SQLAlchemy。服务端统一实现状态判定，列表、详情与日期查询使用同一规则。以下路径均以受保护的 `/api/v1/admin` 为前缀。无有效登录返回 401，游客返回 403；记录不存在返回 404，关系或状态冲突返回 409，字段及日期校验失败返回 422。

| 接口 | 用途 |
|---|---|
| `/suppliers`、`/suppliers/{id}` | 集合 GET/POST，单条 GET/PATCH/DELETE。支持按名称和状态筛选。停启用走 PATCH。 |
| `/products`、`/products/{id}` | 集合 GET/POST，单条 GET/PATCH/DELETE。支持商品名、供应商、类型、上下架筛选。列表返回供应商名、POI 摘要和报价数 `offer_count`。 |
| `/pois` | GET，按城市、关键词和适用地点类型返回可绑定的来源、ID、名称和城市。 |
| `/products/{id}/offers`、`/products/{id}/offers/{date}` | 集合 GET/POST，单日 PATCH/DELETE。GET 可按日期范围、报价状态查询。指定有限日期区间进行自查时返回逐日结果，明确缺价日。 |
| `/products/{id}/offers/batch` | POST，提交起止日期、成本、售价、报价状态和显式覆盖选项，返回新增和更新数。 |

列表支持分页及总数；商品列表报价数定义为该商品**所有实际存在的每日报价记录数**，包含停售和历史日期。用数据库聚合查询，零条也显示 0。批量更新同一天不增加计数。商品详情内所有报价写操作都校验路径中的商品归属，提交后刷新明细和列表计数。

| 页面 | 运营操作与反馈 |
|---|---|
| 供应商列表 `/admin/suppliers` | 搜索、筛选、查看结算主体和状态，打开详情或新建/编辑表单；停用前提示会影响下属商品，删除时展示依赖冲突。 |
| 商品列表 `/admin/products` | 展示商品名、供应商、类型、POI、上下架状态和“报价 N 条”。新建或编辑时按类型切换规格，选择供应商与 POI。点击商品名或报价数进入同一详情页。 |
| 商品详情 `/admin/products/:id` | 上部展示所属供应商、POI、规格及计价单位，下部嵌入报价列表和日期筛选。可新增单日价、批量填价、改价、停售、恢复和删除，明确展示缺价或受上级状态影响的日期。 |

在现有 `AdminLayout.vue` 的资源管理导航下增加“供应商”“商品”两个入口。报价从商品详情维护。三个页面均具备加载、空列表、查询失败重试和保存失败反馈；保存失败保留表单内容。

## 四、建表、迁移与副作用

- **当前基线直接建三表。** 接入现有 `Base.metadata` 与启动建库流程，为商品供应商外键、常用查询字段建立必要索引。验证现有库升级和空库初始化均可重复执行。酒店 POI 估价以及已确认或待确认路书的历史金额继续作为原业务数据保存，不自动导入企业价库。
- **有旧价库的环境单独核对实表。** 若实施时发现同名旧表或另一分支已有价库，先检查实际字段、约束、币种及单位，备份后在副本演练。按可验证的供应商和商品标识建立映射，把重复规格归入商品，将成本、售价、日期和状态迁到日报价；缺成本、缺归属或同商品同日价格冲突须列出原记录交运营核对。映射未解决前保留原表并停止切换。迁移后按商品与日期对账，核对记录覆盖、成本、售价、状态及重复执行结果，再切换读写。不得凭同名酒店合并商品或用推测值补齐成本。
- **失效和删除的影响。** 停用或下架会影响整批日期的实际可售结果，运营界面应提示影响范围。父记录删除受引用保护，普通状态切换优先使用停用、下架或停售。
- **对外数据边界。** 成本、结算主体及供应商联系方式属于后台信息。后续 C 端核价接口应使用独立响应模型，仅返回允许游客查看的售价、规格和可售结果。

## 五、实施顺序与验收

先在 `backend/app/db` 定义模型和迁移，再完成受运营权限保护的资源服务与接口；接入 Vue 后台导航和表单，最后按下表验证。后端自动化用例放在 `backend/tests/`，使用隔离数据库及模拟 POI 返回，不依赖真实高德密钥。

| 场景 | 验收标准 |
|---|---|
| 供应商与商品维护 | 两名运营均可查询和维护同一企业的数据。供应商及三个类型商品均可增改查。空父记录可删除，有子记录返回 409；类型或规格错误返回 422。 |
| POI 关联 | 同一家酒店可绑定两个不同房型。房型或门票缺少适配 POI 时可保存下架草稿，上架受阻；车辆可正常无 POI 上架。外部检索失败后原绑定仍在。 |
| 金额、主键和计数 | 同商品两天分别报 360 元和 420 元，一间两晚售价合计 780 元，报价数为 2。修改或暂停任一天仍为 2，删除一天后为 1；缺价日与 0 元报价可区分。 |
| 三层状态联动 | 启用供应商、上架商品和当日可售报价得到可售结果；逐层停用、下架或停售，各自产生相应原因。恢复上级后，原先单独停售的日期仍停售。 |
| 批量操作及并发 | 批量含已报价日期时默认整批回退，明确覆盖后按天更新。两个请求同时新增同商品同日价格最多产生一条记录，冲突可识别；删除与新增子记录并发时没有孤立数据。 |
| 权限与页面 | 运营可由供应商列表进入商品管理，在商品详情完成报价维护；游客或过期凭证无法通过直接请求获取或修改资源。真实浏览器核对筛选、报价数、状态联动、错误反馈及刷新后的持久化。 |
| 数据升级与回归 | 临时新库、现有结构旧库均成功初始化，重复启动保留数据。保留原账号角色和已有行程、路书金额。覆盖 SQLite；使用 PostgreSQL 交付时补做同类约束、事务及迁移验收。 |

## 验证记录

- 从 `backend/` 在隔离环境运行 `python -m pytest -q`，84 项通过。本次新增 22 个测试场景，包含双运营、三类商品、POI 查询与故障、整分和日期校验、报价计数、三层状态、批量回退、并发冲突和游客权限。
- 临时 SQLite 新库、已有业务表的旧库均通过启动验证。重复启动保留了既有运营角色、密码散列、路书金额和新建报价。验证了实际外键约束，以及发现不兼容的 `price_offers` 表时停止初始化、保留旧记录。
- 从 `frontend/` 运行 `npm run build` 成功。Vite 仍提示有产物超过 500 kB。
- 在真实浏览器使用临时 SQLite 和模拟地图响应。从供应商建档和名称筛选进入商品管理，验证未绑定房型的上架提示、选择酒店 POI、查询失败保留绑定，以及按报价数量进详情。单日报价 ¥360.00 和 ¥420.00 跨夜合计 ¥780.00。核对了批量冲突和明确覆盖、零元促销提示、刷新后报价计数、供应商停启用、报价停售与恢复、缺价日期及游客拦截。
- 日期自查和批量操作单次最多 366 个服务日。单日报价金额上限为 2,147,483,647 分，对应数据库整数范围。跨夜有缺价时不显示完整合计。带报价状态筛选的列表只显示匹配状态的报价，跨夜可售结果始终按完整入住区间计算。
- 高德请求使用独立缓存并按指定城市过滤，使用模拟 HTTP 验证参数和缓存，本地种子查询使用临时 Chroma 实测。真实高德服务与 PostgreSQL 尚未联调。 [高德 POI 搜索文档](https://lbs.amap.com/api/webservice/guide/api-advanced/search)
