# 行程模板管理与发布

任务日期为 2026-11-25。已完成实现，本地验收结果见文末。对应《旅游Agent工作内容清单》企业后台“行程与内容”中的“行程模板”。

## 目标与验收主线

运营登录后台，创建“成都亲子三日游”，编排三天的活动，预览后直接发布。游客端或 Agent 的开发者用已登录账号，通过只读接口取得这一版模板。运营将第二天的安排从公园改为博物馆，保存草稿期间读者仍看到公园，再次发布后才看到博物馆。下架后，新读者无法取得模板，游客之前保存的个人路书仍保留原安排。

沿用单企业、多个同权运营账号。每名运营均可编辑并直接发布企业模板，也可维护其他运营创建的模板。本次交付后台页面、发布服务和已发布模板的读取契约。推荐内容库属于第④项；游客选用模板的页面、将模板生成个人行程的接口、接入 LangGraph 或 MCP、预订及实时核价留给相应迭代。

## 一、运营编辑什么

| 对象 | 字段与用途 | 校验 |
|---|---|---|
| 模板概况 | 标题、主要目的地、适用人群标签、简介、行前提示 | 新建草稿只需非空标题。发布还需主要目的地和至少一天有效安排；标签、简介、提示均可选。 |
| 每日计划 | 当日主题、有序活动列表、当日备注 | 支持增删日期和调序。天数从列表长度计算，展示序号从 1 连续生成。草稿允许空日，发布时每天须有主题且至少有一个有效活动。 |
| 活动 | 时段说明、活动名称、类别、描述、可选关联商品 | 发布时名称和类别必填。类别为游览、餐饮、住宿、交通或其他。时段可写“上午”等文字，活动顺序取列表顺序。 |
| 关联商品 | 从②的商品列表选择一个商品，例如在“入住酒店”活动下关联某房型 | 每项活动可关联零或一个商品。编辑器按商品名、类型检索，允许纯文字安排。商品引用由运营接口根据 ID 校验。 |

模板用“第几天”表达相对日程。运营调整日序或活动顺序时，相关内容随条目一起移动。天数、版本号、操作人等派生值由服务端生成；正文按纯文本显示。沿用 Pydantic 定义模板专用输入和输出模型，列表、字符串长度限制由前后端共享约定，校验错误定位到具体日期与活动。游客路书的 `Itinerary`、`DayPlan` 带有实际行程、估价等字段，未来由取用方按需要映射。

前后端约定每个模板最多 30 天、每天最多 30 个活动、最多 12 个人群标签。标题 160 字符、目的地 100 字符、标签 30 字符、简介 2,000 字符、行前提示 3,000 字符。日主题 120 字符、日备注 1,500 字符，活动时段 60 字符、名称 160 字符、描述 1,000 字符。

**与资源管理的衔接。** 发布时在服务端重查每个已选商品，要求商品存在、已上架、供应商已启用。校验失败时指出相应日程和商品，允许运营替换或解除关联。发布快照只保存商品 ID、当时的名称和类型。模板没有指定入住日或游览日，发布不要求已有某日报价。快照中的商品是参考安排；以后下架、改名或缺价，读者看到的已发布文案保持稳定，实际选购时须另查当日可售条件。成本、结算信息和运营备注不进入读者响应。

## 二、草稿、发布和下架

区分两个维度：当前是否对外可见，以及是否有尚未发布的修改。比如同一模板可以是“已发布 v1 · 有草稿修改”。

| 操作 | 后台结果 | 只读接口结果 |
|---|---|---|
| 新建、首次保存 | 一份工作草稿 | 列表无此项，详情 404 |
| 首次发布 | 对当前已保存草稿做完整校验，成功后生成 v1 | 列表和详情可读 v1 |
| 编辑已上线模板并保存 | 工作草稿更新，后台提示有未发布修改 | 标题、筛选结果、排序依据、详情内容均继续使用线上快照 |
| 再次发布 | 生成下一版并一次性切换线上版本；内容无变化且已上线时提示“已是最新发布版本” | 成功后读取完整新版，失败时继续读取原版 |
| 下架 | 隐藏线上版本，保留工作草稿、历次快照和版本计数 | 列表立即移除，按已知 ID 读取也返回 404 |
| 下架后恢复发布 | 重新校验当前已保存草稿，生成下一版；比如 v2 下架后再发布为 v3 | 只有新发布版本重新可读 |

预览展示运营正在编辑的内容，注明“草稿预览”；未保存编辑应先保存成功再发布。任一登录运营可查看当前线上效果。首版通过下架停止分发，保留已发布记录。版本回滚、多人审批和定时发布均在后续需求出现时单独设计。

## 三、存储与并发

使用现有 SQLAlchemy 和应用数据库。建议采用一条可编辑主记录、每次发布一条不可变快照。这样“保存草稿”和“让游客看到”可以独立验收。

| 表 | 必要数据 |
|---|---|
| `itinerary_templates` | 稳定模板 ID、草稿内容（结构化 JSON）、当前可见性（草稿／上线／下架）、最新发布版本号（首次为 0）、编辑修订号 `revision`、创建及最近操作的账号 ID 和时间。 |
| `itinerary_template_versions` | 模板 ID、发布版本号、完整对外内容快照、发布人和时间。为列表检索存该版本的标题、目的地、天数，均从发布内容生成。外键指向模板，模板 ID 与版本号组合唯一。 |

- 模板与个人 `trips`、`trip_versions` 独立存储。未来生成个人路书时应复制选中的发布内容，可记录来源模板 ID 和版本；之后读取路书按游客自己的快照。编辑、发布、下架操作只写模板表。
- 保存、发布和下架请求都带打开页面时取得的 `expected_revision`。服务端按修订号条件更新；成功写入后修订号递增。同一事务中完成发布校验、分配版本号、插入快照和更新线上状态。两名运营同时操作时，较旧的写入返回 409；双击发布或超时重试不会生成两个相同发布。前端保留未提交内容，提示重新加载并核对。
- 只读列表和详情统一按“已上线 + 主记录指定的发布版本”检索。搜索标题、目的地、天数以及分页总数均从读者可见的版本计算。首版读取最新数据，避免下架后由旧缓存继续分发。
- 将新增模型接入现有建表流程，验证 SQLite 空库、已有业务库升级和重复初始化。兼容项目的 PostgreSQL 配置。既有个人行程、资源及价格记录无需转换为模板。

## 四、接口与页面

管理路由挂在现有 `/api/v1/admin` 下，继承整组运营鉴权；读者接口使用现有登录依赖，未来游客页面与 Agent 可共用。以下为相对于 `/api/v1` 的路径。

| 接口 | 契约 |
|---|---|
| `GET /admin/itinerary-templates` | 按草稿标题、目的地和可见性筛选，分页返回模板 ID、标题、天数、状态、最新发布版、是否有未发布修改及最近更新时间。 |
| `POST /admin/itinerary-templates` | 新建草稿，返回 201、模板 ID 和修订号。 |
| `GET /admin/itinerary-templates/{id}` | 返回完整工作草稿、修订号、可见性及最新发布版本信息。 |
| `PUT /admin/itinerary-templates/{id}/draft` | 按修订号保存完整可编辑内容，返回新的草稿状态。 |
| `POST /admin/itinerary-templates/{id}/publish`、`POST /admin/itinerary-templates/{id}/unpublish` | 分别发布已保存草稿、下架线上模板。返回变更后的状态、修订号及最新发布版本号。 |
| `GET /itinerary-templates`、`GET /itinerary-templates/{id}` | 已登录账号查询当前发布内容。列表按标题、目的地、天数筛选并分页，按最近发布时间与 ID 稳定排序，返回摘要、适用人群及版本；详情补全逐日活动和提示。两者使用面向读者的响应模型。 |

无有效登录返回 401，游客访问管理接口返回 403；资源不存在或读者访问不可见模板返回 404；更新冲突返回 409；发布资料不完整、关联商品失效等可纠正的输入问题返回 422。所有失败操作保留原线上状态。

在现有 `AdminLayout.vue` 增加“行程与内容 → 行程模板”。复用 Vue、Element Plus 和现有认证请求方式。

1. **列表页** `/admin/itinerary-templates`。提供查询、筛选、新建、编辑、查看线上版和下架。并列显示线上版号与草稿修改提示。下架前显示模板名称和影响范围。
2. **新建、编辑页**。上部填基本资料，下部逐日添加、删除及移动日期和活动，活动可选商品。提供保存、预览、发布；预览沿用同一内容渲染组件。离开有未保存修改的页面时提示。发布成功展示实际版号，失败定位到出错字段；网络异常保留输入以便重试。
3. 后台的“查看线上版”从只读详情接口加载，确保运营看到游客能取得的内容。草稿预览仅对有运营权限的账号开放。

## 五、测试与交付

后端行为测试放在 `backend/tests/test_itinerary_templates.py`，使用临时库和两名运营、一名游客。前端按下列场景执行真实浏览器验收。

| 场景 | 通过条件 |
|---|---|
| 首次创建与发布 | 只填标题能存草稿，游客列表与详情均读不到。空日发布收到 422，补齐后首次发布为 v1。 |
| 日程编辑 | 新增、移除、移动日期和活动后，保存、刷新、预览与发布所得顺序一致，天数与连续日序正确。 |
| 草稿隔离 | v1 上线后修改草稿的标题、目的地及第二天活动。后台能读到修改；读者按新标题搜索无结果，按旧标题仍查到 v1。重新发布后，列表和详情同时切换到 v2。 |
| 商品关联 | 无商品的纯文字模板能发布。关联有效商品可发布；发布前商品下架、删除或供应商停用时，返回准确位置，线上版仍可读。发布后商品改名不改写已有快照。 |
| 下架与再发布 | 下架后列表无结果、详情 404，运营仍可编辑。重新发布后版号递增，历史快照内容及测试库中已有个人路书均保持原值。 |
| 并发与失败 | 两名运营从同一修订号编辑，一方成功，另一方得到 409。重复发布不产生额外版号；模拟发布事务中途失败时没有半条快照或错误线上指针。 |
| 权限与界面 | 未登录读者 401，游客直接调用任一后台写接口 403。浏览器走通列表、新建、保存、预览、发布、查看线上版和下架；核对刷新、错误提示和未保存编辑提示。读者响应无员工信息或成本。 |

实施顺序为数据模型及服务、管理与只读接口、后台页面、自动化测试与浏览器验收。交付者在 `backend/` 运行全量 pytest，在 `frontend/` 运行 `npm run build`，回填测试结果、浏览器走查和未验证项。

## 验证记录

- 在 `backend/` 使用隔离测试环境运行全量 `python -m pytest -q`，94 项通过，其中 10 个模板用例。覆盖标题草稿、字段及商品校验、上线版本的筛选与排序、下架和版本累进、账号权限、并发保存和并发发布的 409、发布事务异常后原版本可读，以及个人路书不受影响。
- 临时 SQLite 空库、已有资源和报价的旧库均通过启动和重复初始化验证。通过 PostgreSQL 方言编译检查两张新表的建表语句和可见版本查询，尚未在真实 PostgreSQL 实例运行。
- 在 `frontend/` 运行 `npm run build` 成功，Vite 保留大于 500 kB 的包体积提示。
- 在真实浏览器和临时 SQLite 中完成新建、首次保存后进入编辑页、刷新、增删与调序、草稿预览、商品选择、发布和下架。核对空日发布的字段提示、纯文本展示、v1 的公园安排在草稿修改后继续可见、v2 发布后显示博物馆、下架后重新发布为 v3，以及重复发布保持原版号。
- 浏览器也验证了未保存编辑的离开提示、模拟保存 503 后保留输入与重试、旧修订冲突保留当前表单、关联商品下架时定位到对应活动并保留原线上商品快照。
