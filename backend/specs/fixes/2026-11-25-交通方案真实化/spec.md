# 交通方案真实化：城内直出与城际区间预估

## 原因与目标

`transport_node` 只调用一次大模型，输入仅出发城市、目的地、天数，没有任何外部查询，却要求模型输出具体发车时刻、到达时刻和票价。结果是行程里的交通全部为模型生成：车次时刻、票价、站名都不来自任何数据源。同时 `route_node` 已经算出了每天的景点顺序、总距离、交通方式与耗时，但这些结果没有被使用，城内交通被重新编造，起点常写「酒店」，与真实游览顺序无关。

目标：

- 城内交通改成由路线结果**代码直出**，不再经过大模型，也不再伪造发车时刻。
- 城际交通改为**区间预估**并强制标注，去掉伪造的具体时刻与精确票价。
- 交通费用改为可复算的口径，不再随机。

## 范围和边界

### A. 城内交通：改用路线结果直出

输入：`state["routes"]`（`day`、`attraction_ids`、`total_distance_km`、`travel_mode`、`estimated_travel_time_minutes`）、当天 `Attraction` 的 `name` 与 `location`、当天 `hotel`。

要求：

1. 段序按当天景点顺序生成：首段「酒店 → 第 1 个景点」，中间「景点 i → 景点 i+1」，末段「末景点 → 酒店」。
2. 每段距离独立按两点坐标计算（复用现有 haversine 实现），不按总距离平均分摊。
3. 交通方式沿用当天 `route.travel_mode`。
4. 每段耗时按该方式的固定速度换算，速度口径与现有 `_estimate_travel` 保持一致。
5. 每段票价 = 单价表 × 1（**单人单段**），与既有 `TransportOption.price_cny` 语义一致；人数换算仍由预算环节统一处理，避免重复乘人。
6. 单价表放入配置而非硬编码在逻辑中（取值见「已确认决策」）。
7. `departure_time` 与 `arrival_time` 留空，不再输出伪造时刻。
8. 该步骤不调用大模型；模型不可用时城内交通仍应正确生成。
9. 边界：当天无酒店时首段与末段都不生成；当天只有 1 个景点时生成「酒店 → 景点」与「景点 → 酒店」两段；当天无景点时不生成交通段。

### B. 城际交通：改为区间预估

触发条件：`departure_city` 非空且与 `destination` 不同。

要求：

1. 输出结构改为区间形态：交通方式、起止城市、耗时区间、票价区间、`is_estimate = true`、提示文案「预估区间，请自行比价」。
2. 允许由模型给出区间，但**禁止输出具体发车/到达时刻**；提示词与结果校验双重约束。
3. 校验区间合法性：最小值不得大于最大值；票价区间宽度不得超过下限的 2 倍。校验不通过的条目丢弃，不写入结果，也不报错。
4. 去程与返程各给出建议，并**同时给出高铁与航班两种方式**各自的耗时区间与票价区间（例如「北京→上海」给高铁约 4.5–5.5 小时、¥550–660，航班约 2–2.5 小时、¥700–1200）。两地距离过近、航班明显不适用时可只给高铁，但每种走向至少给出一种可行方式。不列具体班次。
5. 展示上归入「建议/参考」，不进入可预订列表。

### 数据结构调整

- 城内交通：沿用 `TransportOption`，`price_cny` 为单人单段价，时刻字段留空。
- 城际交通：新增独立模型（如 `IntercityEstimate`），不复用 `TransportOption`，避免时刻字段被误填。
- `TransportPlan.intercity` 类型随之调整；`DayPlan.transport` 保持列表形态。
- 前端类型定义与详情页渲染同步调整；**旧行程必须仍能正常渲染**（旧数据带有时刻与单值票价），详情页需兼容两种形态。
- MCP 工具的 markdown 摘要不含交通行（只渲染路线），无需改动；其附带的完整 JSON 会自然包含新字段。

### 预算口径

- 城内交通：沿用现有口径 `(门票 + 餐饮 + 城内交通) × 人数 + 住宿`。
- 城际交通：按区间中值计入，明细中单列「城际交通（预估）」并标注预估。
- 城际不参与「可预订总额」的计算，只作参考金额展示。

### 非目标

- 不接入 12306、航司或 OTA 接口。
- 不修改 `route_node` 的聚类与路径算法。
- 不把城际线路纳入价库（作为后续独立迭代）。
- 不调整景点、酒店、餐厅的检索与推荐逻辑。

### 可能受影响的现有行为

- 城内交通段数由「模型随机给出」变为「按景点顺序确定生成」，条目数量通常增加。
- 详情页不再显示交通发车时刻，原先依赖该字段的展示需调整。
- 城内交通金额由单价表决定，可能与历史金额不同；城际由单值改为区间中值。
- 已保存的历史行程仍为旧结构，渲染逻辑必须向后兼容。

## 验收与回归

1. 城内交通的段序与当天景点顺序严格一致，含「酒店 → 第 1 个景点」首段与「末景点 → 酒店」末段；每段起止点为真实地点名，不含编造站点。
2. 城内交通不出现发车/到达时刻。
3. 城内交通金额 = 单价表 × 段数，且为单人价；按人数换算后与费用明细一致。
4. 确定性：同一份路书重复生成，城内交通的段与金额完全一致，不受模型随机性影响。
5. 城际交通不出现具体时刻，展示为区间并带「预估」标识；同一走向同时给出高铁与航班两种方式的耗时与票价区间（短途可只给高铁）。
6. 城际区间校验不通过时该条被丢弃，流程不报错、不中断。
7. 旧行程（带时刻、单值票价）在详情页仍可正常打开与展示。
8. 替换或关闭大模型后，城内交通仍能正确生成。

## 测试与回归计划

新增后端用例，使用构造的 routes / attractions / hotel，不依赖网络与模型：

1. `test_intraday_transport_follows_attraction_order`：段序、起止点、段数与景点顺序一致，且首段来自酒店、末段回到酒店。
2. `test_intraday_transport_amount_uses_unit_price`：金额等于单价表 × 段数，且为单人价。
3. `test_intraday_transport_edges`：无酒店（无首末段）、单景点（往返两段）、无景点（无段）三种边界。
4. `test_intercity_estimate_rejects_invalid_range`：min > max、区间过宽两类非法输入被丢弃。
5. `test_intercity_estimate_has_no_times`：区间结果不含具体时刻。
6. `test_intercity_estimate_covers_train_and_flight`：常规城际走向同时给出高铁与航班两种方式的区间；短途仅高铁时也合法。

回归：`itinerary_costs` 的总额计算、历史行程详情页渲染、MCP `get_trip` 输出。

## 已确认决策

1. 城内交通含首段「酒店 → 第 1 个景点」与末段「末景点 → 酒店」。
2. 城际区间由模型预估，且需同时给出高铁与航班两种方式的区间，强制标注「预估」，待价库接入线路报价后替换。
3. 城际按区间中值计入总预算，并单独标注为预估。
4. 单价表：步行 0、地铁 3 元/段、公交 2 元/段、打车起步 13 元 + 2.5 元/公里（按段距离计算并取整到 0.5 元）。

## 验证记录

实现位置与规格的差异（均为落地时的必要调整）：

1. **城内交通在编译器生成**，不在 `transport_node`。因为景点分日由编译器决定，只有在编译完成后按最终 `day_plans` 的顺序生成，才能保证“交通顺序 = 展示顺序”。节点只负责城际。
2. `TransportOption` 新增 `duration_minutes` 字段。规格要求按方式换算每段耗时，但没有承载字段，故补充；旧数据无该字段时默认为 0，前端回退显示原时刻。
3. 城际预估放在 `Itinerary.intercity_estimates`（顶层），不塞进 `day_plans[].transport`，避免与城内段混淆、也避免时刻字段被误填。
4. `transport_node` 在未提供出发城市、或出发城市与目的地相同时**不调用模型**（`llm_calls=0`），比原来少一次调用。
5. 新增 `app/services/geo.py` 承载 haversine，`agents.py` 改为复用，避免两处各写一份。
6. 单价表新增 5 个配置项 `transport_walk/bus/metro_fare_cny`、`transport_taxi_base_cny`、`transport_taxi_per_km_cny`。
