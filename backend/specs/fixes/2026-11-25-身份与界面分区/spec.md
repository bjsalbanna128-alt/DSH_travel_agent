# 身份与界面分区：游客只看 C 端、运营只看 B 端

## 原因与目标

登录身份与界面区域没有严格对齐，出现两种混合：

1. 游客登录后可能被送到 `/admin`，被守卫拦下并弹出「需要运营身份才能访问企业运营后台」，随后退回首页。
2. 运营登录后可以正常进入并停留在 C 端页面（首页、规划、聊天、行程详情、历史、个人中心）。

根因有两处：

- `loginDestination` 只校验 redirect 不是 public 路由，未校验目标区域是否属于当前角色。带 `?redirect=/admin` 时会让游客跳到 `/admin`。
- C 端路由没有身份限制。`/`、`/plan`、`/chat`、`/trip/:id`、`/trip/:id/edit`、`/history`、`/profile` 均未声明 `touristOnly`，因此运营访问时不被拦截。

附带问题：`checkOperatorRoute` 作为判断函数在拒绝时直接弹出提示，副作用与判断耦合；`role` 未就绪时两个分支都不触发，存在短暂放行。

目标：

- 身份与区域一一对应：`tourist` 只能进入 C 端区域，`operator` 只能进入 B 端区域。
- 跨区域访问一律静默跳转到本区域首页，不渲染对方界面，也不弹出越权提示（那不是错误，是走错门）。
- 只有真正的越权操作（接口返回 403）才提示「需要运营身份」。
- 角色尚未确定时不放行任何非公开页面，避免闪现对方界面。

## 范围和边界

### 一、路由模型改为按区域声明

1. 在路由 meta 中引入区域标记 `area: 'c' | 'b'`，替代现有分散的 `operatorOnly` / `touristOnly`。
2. C 端全部路由标记 `area: 'c'`：`/`、`/plan`、`/chat`、`/trip/:tripId`、`/trip/:tripId/edit`、`/history`、`/profile`、`/messages`、`/messages/:id`、`/tickets`、`/tickets/:id`。
3. B 端父路由 `/admin` 标记 `area: 'b'`，子路由继承。
4. 公开路由保持 `public: true`：`/login`、`/register`。

### 二、守卫规则

1. 公开路由直接放行。
2. 未登录：跳登录页，并带上 `redirect`。
3. 已登录但 `role` 尚未就绪：先 `syncSession`，仍未就绪则跳登录页；**不允许放行**。
4. `role` 就绪后按区域比对：
   - 目标区域与角色匹配 → 放行；
   - 不匹配 → 静默跳转到该角色首页（游客 `/`，运营 `/admin`），**不弹出任何提示**。
5. 禁止在守卫或判断函数内部触发 UI 提示（如 `ElMessage`）。提示只能由「用户主动点击了无权入口」或「接口返回 403」这两种明确场景触发。

### 三、登录落地页

`loginDestination` 必须同时校验两点：

1. `redirect` 不是公开路由；
2. `redirect` 指向的区域与登录角色一致。

任一不满足则忽略 `redirect`，按角色落到默认首页：游客 `/`，运营 `/admin`。

已登录用户访问 `/login` 或 `/register` 时，直接按角色跳转默认首页（目前 `/login` 由页面自己处理，容易与守卫重复，统一收到守卫里）。

### 四、布局与区域切换

1. `App.vue` 的布局分支按区域判断，而不是只按 `operatorOnly`：C 端渲染 C 端头部与容器，B 端渲染 `AdminLayout`，两者不得同时出现。
2. 角色变化（登出、切换账号、会话刷新）时：
   - 清空上一个角色的界面状态（现有 `travel` store、消息轮询、未读计数）；
   - 若当前路由不属于新角色区域，跳转到新角色首页。
3. 角色未就绪时不渲染任何一方主体内容，只显示「正在验证登录状态」。

### 五、非目标

- 不做细粒度权限矩阵（如运营内部区分客服、财务、只读）。
- 不修改后端鉴权（`require_operator` 已存在），本次只修前端分区。
- 不改变任何业务页面的功能与数据。
- 不为运营开放 C 端行程链接的只读例外。运营查看用户行程由 B 端独立的行程查询入口承担，作为后续迭代，不在本次范围内。
- 不引入前端测试框架。

### 六、可能受影响的现有行为

- 路由 meta 从 `operatorOnly` / `touristOnly` 改为 `area`，所有引用处（`App.vue`、`useInboxPolling`、`InboxPage`、`InboxDetailPage`、`TicketListPage`、工单相关 API 调用）需要同步。
- `InboxPage` 与 `TicketListPage` 被 C 端与 B 端共用，改为读取 `area` 判断请求前缀，行为不变。
- 运营直接访问 C 端链接（如用户分享的行程详情）不再是「可浏览」，而是跳回 `/admin`。这是刻意收紧；运营查看用户行程改由 B 端行程查询入口承担，后续单独迭代。
- 已登录用户访问 `/login` 会立即被跳走，登录页不再自己处理跳转。

## 验收与回归

1. 游客登录（无 redirect）落在 `/`，页头只出现 C 端导航项，不出现任何运营字样。
2. 游客登录时带 `?redirect=/admin`，落在 `/`，**不出现**「需要运营身份」提示，也不出现 `/admin` 界面。
3. 游客手动访问 `/admin`，静默跳回 `/`，不弹提示（可用 `/admin` 直接输入验证）。
4. 运营登录落在 `/admin`，页头与侧栏只有 B 端内容。
5. 运营访问 `/`、`/plan`、`/chat`、`/trip/:id`、`/history`、`/profile` 中任意一个，均跳回 `/admin`，且**不出现 C 端界面闪烁**。
6. 已登录状态访问 `/login`：游客跳 `/`，运营跳 `/admin`。
7. 会话未就绪（刷新页面、token 校验中）时不渲染任何一方主体，只显示登录状态提示；校验完成后落到正确区域。
8. 游客主动点击无权入口或接口返回 403 时，仍可看到一次「需要运营身份」提示（保留该反馈）。
9. 角色切换（登出后登录另一角色）后，上一个角色的界面状态与未读轮询计数被清空。
10. 前端构建通过；C 端与 B 端主要页面手工走查无混合。

## 测试与回归计划

前端无自动化测试框架，本次采用构建 + 手工核对清单：

1. `npm run build` 通过。
2. 按验收 1–9 逐条手工验证，记录实际结果。
3. 回归：C 端规划 → 草稿 → 确认全流程；B 端资源管理与模板管理基本操作；消息与工单在两侧的读写。

后端无需改动，回归时确认 `/api/v1/admin` 仍受 `require_operator` 保护（游客直接调用返回 403）。

## 待定项

1. 「走错区域」是否需要一个极简提示（如一次性 toast「已切换到运营后台」）。默认完全静默。
2. 是否保留 `operatorOnly` / `touristOnly` 作为兼容别名。默认不保留，统一迁移到 `area`，避免两套语义并存。

## 已确认决策

1. 不通过 C 端行程链接向运营开放查看权限。运营访问 `/trip/:id` 等 C 端路由一律跳回 `/admin`，不设例外。
2. 运营查看用户行程改为 B 端独立的行程查询入口（按行程号/用户/时间检索），作为后续独立迭代，本次不实现。
